## 2. 候选机会（至少 3 个，均为创新切入点而非照抄）

### 候选 A：对味 Duìwèi — coding agent 选型的「决策说明书 + 口味校准台」（买方侧）
- 创新切入点：把 agent 在一次 PR 里**悄悄做完的依赖 / 库 / 工具选型决定**变得可读（为什么加、考虑过哪些替代、逐轴权衡），再从你对几个例子的判断里**学出一份可复用的「选型口味档案」**，回放到本次 PR 去改判（哪些翻盘、避免哪些后悔、省多少体积 / 传递依赖 / 许可硬伤）。**不是 gate、不是扫描器**：治理的是 agent 的「选择过程 + 品味」。
- 目标用户 / 场景：用 coding agent（Cursor / Claude Code / Origin Cloud Agent）高频产出代码的团队 / 技术负责人；每个 agent PR 都在做无人复核的供应链与架构选型。
- 五维评分：痛点 5/5，机制新意 4/5，方向相关 5/5，一天可行性 5/5，启发价值 4/5 → 合计 **23/25**

### 候选 B：被 Agent 选中体检 — devtool 厂商侧「你的库能被 agent 正确发现 / 理解 / 调用吗」
- 创新切入点：骑乘 Gauge + 「MCP 成默认出口」+ Balsa（机器可读规格）——厂商把 README / API / MCP schema 丢进来，模拟 coding agent 为某任务评估它：能否被发现、知不知道何时用、调用参数对不对，还是选了竞品 / 幻觉出错误用法；before/after 展示「改文档 → 被采纳」。
- 目标用户 / 场景：devtool / API / MCP 厂商的 DevRel / GTM。
- 五维评分：痛点 4/5，机制新意 3/5（「模拟 agent 读文档并判断」与既有的意图→工具消歧、接收模拟同源），方向相关 5/5，一天可行性 4/5，启发价值 4/5 → 合计 **20/25**

### 候选 C：常驻 Agent 值守台 — 骑乘 Cronloop 的「这个循环还值不值得跑」
- 创新切入点：定时 agent（Cronloop）容易变僵尸——每轮起干净沙箱、durable memory 会腐坏，悄悄没产出却一直花钱。做一个「常驻 agent 组合」视图，判定每个循环是「仍有价值 / 在漂移 / 已成僵尸」并给出理由。
- 目标用户 / 场景：跑很多定时 / proactive agent 的团队。
- 五维评分：痛点 3/5（Cronloop 早期、小团队信号弱），机制新意 3/5（花费 / 值守 digest 形态已多次被做），方向相关 4/5，一天可行性 4/5，启发价值 3/5 → 合计 **17/25**

> 另考虑但未展开的 2C 候选 D：Skim Recap 式「阅读债」跟踪（你划过多少、最该回看哪 3 段）。判断其与既有的「补看 / 叙事化阅读」角度高度重叠，且端侧模型价值纯前端难以可信呈现，评分约 16/25，弱于 A，故不选。

## 3. 最终选择

- 选中：**候选 A — 对味 Duìwèi**，总分 **23/25**
- 为什么选它（相对其他候选的优势）：
  1. **痛点最真实且正在快速放大**：agent 写的代码越多，它替你做的**不可逆供应链选型**就越多，而这层今天几乎无人复核——这是 Origin「合并闭环」也兜不住的缺口。
  2. **切入角度最新**：报告把「agent-led」只讲到卖方（Gauge），**买方侧是空白**；且我刻意避开这一波做烂的「gate / 扫描 / 审批门」形态，用「决策透明 + 口味校准」这一**新形态**切入。
  3. **一天可做出可信 Demo**：选型决策 + 口味评分是确定性、可解释的纯前端体验，mock 一次真实感的 agent PR 即可讲透，无需真实 registry / LLM。
  4. **启发价值**：它把「Agent-Led Growth」从厂商 GTM 反转为买方治理，并提出一个更普适的产品面——**当 agent 自主决策时，「品味 / 偏好」的显式采集与复用本身就是一个新产品层**。

## 4. 深入论证（针对选中机会）

1. 目标用户：用 coding agent 高频产出代码的工程团队 / 技术负责人（尤其重视供应链、体积、许可、可维护性的中后台 / SaaS 团队）。高意图、可付费（供应链事故与技术债成本高）。
2. 核心痛点（真实、高频、可付费）：agent 每개 PR 都在替你「采购」——装 moment 而不是原生 Intl、为一行补零装一个 40 个月没维护的包、选了 AGPL 的邮件库、为一个简单 POST 引入 axios……这些资深工程师会反复权衡的决定，agent 一笔带过且**无人复核、事后难回滚**。人工逐个盯 PR 的依赖变更既累又不成体系。
3. 现有产品为什么没解决好：**Gauge** 只做卖方（帮厂商被选中）；**Snyk / Socket** 是对既有产物扫 CVE / 许可（治理的是产物，不是 agent 的**选择过程**，也不理解你的**口味**）；**Dependabot** 只管版本升级；**Origin** 的合并闭环把关 diff，兜不住「这个依赖该不该进来 / 该换成什么」。没有人把「让 agent 按你的品味选型」当成一个可教、可复用的产品。
4. 为什么适合做轻量 Demo：核心价值＝把沉默的选型决策**可视化** + 从几次判断**学出口味** + **before/after 改判**，天然契合纯前端「模拟体验 + 价值可视化」；评分逻辑确定性、可展示公式，全 mock 即可讲清「解决什么 / 怎么用 / 增量在哪」。

## 5. 不照抄声明（四项必填）

1. 创新切入点是什么：站在**买方**一侧，把 coding agent 沉默的**选型决策过程**变可读，并从用户判断里**蒸馏出可复用的「选型口味档案」**，回放去改判 agent 的依赖 / 库 / 工具选择。
2. 解决的具体问题 / 场景：agent 每次 PR 都在做无人复核、事后难回滚的供应链 / 架构选型（体积、维护、许可、传递依赖、类型、该不该用原生），而团队既无透明度、也无法把「自己的品味」教给 agent。
3. 相对被参考产品的增量价值（差异点）：对比 Gauge（卖方 GTM）→ 我做买方治理；对比 Snyk/Socket（扫既有产物的 CVE/许可）→ 我治理 agent 的**选择过程**并引入**口味**这一维度；对比 Dependabot（版本升级）→ 我关心「该不该用 / 换成什么」；对比这一波治理产品（运行时 gate / 审批门）→ 我用**决策透明 + 口味校准**而非拦截。
4. 为什么这不是照抄 Gauge：Gauge 的用户是**想被 agent 选中的厂商**，价值是分析 + 内容引擎；对味的用户是**用 agent 的团队**，价值是让 agent 的选型**对我的口味**、且这份口味可学习、可复用。二者服务对象、价值链位置、产品形态完全相反——是同一结构性趋势（agent 成为选型主体）的**镜像另一侧**。

## 6. 不确定性与风险

- 需求侧风险：可能被视为「Cursor / Origin 迟早内置的一个功能」而非独立产品；付费意愿需验证（是买方付费，还是被平台吸收）。缓解：先做厂商中立、跨 agent / 跨 harness 的「口味层」，价值在于**可复用、可携带的团队品味档案**，这是单一 IDE 内置功能难覆盖的。
- 落地 / 技术风险：真实产品要拿到 agent 的选型理由（需 agent 暴露 rationale）+ 实时 registry 数据（npm / deps.dev / OSV）；「口味 → 改判」的映射要足够透明、不能变成又一个不可解释的黑箱。Demo 里我用**确定性可解释公式**并在 UI 里完整展示，正是对这一风险的回应。
- 我可能判断错的地方：也许多数团队对「依赖品味」并不敏感（只要能跑就行），痛点强度被我高估；或「口味校准」在真实高频场景里维护成本过高。若如此，应收窄到**许可 / 供应链合规**这一硬痛点先立足，再扩展到体积 / 维护 / 原生等软偏好。
