## 1. 报告事实 vs 我的独立判断

| 维度 | 报告怎么说（参考资料） | 我作为创业者的独立判断 |
| --- | --- | --- |
| Zero 的价值 | 「把 agent 当编译器第一读者」贯彻到语言/工具链，是面向 Agent 的彻底做法（16/18） | **认同其洞察，质疑其形态。** 报告也如实标注 Zero「实验性、v0.3.x、图优先迁移成本高、生态与真实采用是最大不确定，可能长期停留在研究基座」。我押注：**「语义级、机读、少猜」的价值是对的，但让全世界改用一门新语言去获得它，是最贵的路径**。真正可迁移、当下能用的价值，是把「语义级意图」的思想**回填到现有语言/现有 agent 工作流**里，而非另起炉灶。 |
| 「agent 改错行、靠猜文本」是谁的锅 | 报告归因于「编译器输出是散文、agent 只能爬文档猜文本」——即**读**的问题（诊断输出不结构化） | **我认为下游还有一个更高频、更被忽视的「写」的问题：人给 agent 下达结构性改动时用的是「散文式指令」。** 「把 charge 改个更清楚的名字、postJson 顺便支持 options、金额都用 Cents」——这句话里藏着 3~4 个人没拍板的决策（叫什么名？opts 必填还是选填？金额范围含不含退款？），agent 只能替你猜，于是少改/错改/过度改。Zero 治「编译器→agent」的读，我要治的是**「人→agent」的写**：这一段今天几乎是纯自然语言，零结构、零可复核。 |
| 「一等用户从人转向 Agent」 | 报告当作方向性结论（工具链都在重构成机器可读） | 部分认同、并要修正。**在可预见的很长一段时间里，结构性改动的「意图」仍来自人**。与其幻想把人赶出回路，不如做「人负责编排意图、agent 负责无歧义执行」的**清晰交接面**。一等用户不是非人即 agent，而是**这道人机交接契约**本身。 |

## 2. 候选机会（至少 3 个，均为创新切入点而非照抄）

### 候选 A：编谱 Biānpǔ — 面向 coding agent 的「语义改动谱」编排台（Semantic Change Composer）

- **创新切入点**：不做新语言（Zero 的路），而做一层**厂商中立、覆盖现有语言（TS/JS/Py…）的「结构性改动编排面」**。人不再用散文把重构任务甩给 agent，而是在代码的**符号/依赖图**上，把改动**编排成一份「谱」**（一串带类型参数的语义操作：重命名符号、改签名并传播调用点、改类型、抽取能力/模块、移动符号……）。每加一个操作，实时看到它**展开**成的确切语义编辑集合（触达哪些符号/引用/文件、执行顺序）。最终导出一份**无歧义、机读的操作清单（manifest）**，任何 coding agent 照谱演奏、无需猜文本。
- **目标用户 / 场景**：重度用 coding agent（Cursor/Claude Code/各类 harness）做**跨文件结构性重构**的开发者与团队 lead——他们最常在「一句话交给 agent → agent 少改/改错/过度改 → 来回纠偏几轮」上损耗。
- **五维评分**：痛点 4/5，机制新意 4/5，AI 核心度 4/5，一天可行性 5/5，启发价值 4/5 → 合计 **21/25**

### 候选 B：面向 Agent 的产品表面设计台（Agent-Surface Designer）

- **创新切入点**：承接报告趋势「产品先服务 Agent，再服务人」（Open Analytics/Supernova/Mindcase 把自家能力做成 MCP）。做一个**厂商中立**的设计台：让产品团队**编排「我这个产品向 agent 暴露什么、怎么被读」**（挑哪些事实/工具暴露、如何为 agent 命名与描述、哪些藏起来），再模拟一个 agent 会话去暴露「过度抓取 / 命名歧义 / 误调」的问题。
- **目标用户 / 场景**：正在给自家 SaaS/数据源接 MCP 或 agent API 的产品/平台团队。
- **五维评分**：痛点 4/5，机制新意 3/5，AI 核心度 4/5，一天可行性 4/5，启发价值 4/5 → 合计 **19/25**
- **为何不选**：机制新意与「正名 Zhèngmíng（08-09，MCP 工具消歧）」有明显重叠；且「模拟 agent 会话」重心偏向回放/仿真，一天做扎实的成本更高、也更容易踩到近期已磨损的仿真-回放形态。

### 候选 C：给具体的人做的「人际可玩互动内容」创作器（非 Pocket 克隆的 2C 方向）

- **创新切入点**：Pocket 做的是「面向陌生人 feed 的一次性 meme」（广播式娱乐）。反其道——做「**给你认识的某个人/小群做一件能玩、能回礼的轻互动内容**」，押注**人际互惠**（像好友间来回甩梗图/GIF 那样的留存），而非公开 feed 的病毒式娱乐。
- **目标用户 / 场景**：想低门槛给朋友做点有心意的小互动（生日、内部梗、小测验）的普通消费者。
- **五维评分**：痛点 3/5，机制新意 3/5，AI 核心度 3/5，一天可行性 3/5，启发价值 3/5 → 合计 **15/25**
- **为何不选**：产品价值高度依赖「AI 生成互动内容」这一步，纯前端只能**假造生成**，直接踩中本实验室最警惕的「概念包装/模型自嗨」；且与 Pocket 的克隆边界很难在一天内讲清。低于门槛。

### 候选 D：面向 coding agent 的「事实检索」面（Fact-first Codebase Query）

- **创新切入点**：呼应 Zero 的 `query`（问事实、别猜）。做一层给 agent 用的**结构化事实检索**（符号类型、调用边、能力归属、不变量），让 agent 少爬少猜。
- **五维评分**：痛点 4/5，机制新意 3/5，AI 核心度 4/5，一天可行性 4/5，启发价值 3/5 → 合计 **18/25**
- **为何不选**：与 LSP / Sourcegraph / 各类 code-intelligence 的增量差异偏薄，非照抄声明不够锋利。

## 3. 最终选择

- 选中：**候选 A — 编谱 Biānpǔ（面向 coding agent 的语义改动谱编排台）**，总分 **21/25**
- 为什么选它（相对其他候选的优势）：
  1. **踩在今日最高分信号（Zero 16/18）的正缝上，却走了一条更便宜、当下可用、可迁移的路**——治「人→agent 的写」而非另造语言。这正是报告「对混元 API/Agent 启发」段落里「语义级 patch、让 agent 少猜、可验证」的可落地版本。
  2. **纯前端可信度最高**：核心是一个**确定性的语义图引擎 + 交互编排**，全 mock、零假造 AI 生成——不像候选 C 要假造生成、也不像候选 B/D 重心在难做扎实的仿真/检索。
  3. **形态新鲜**：属「编排/创作（authoring/composition）」基因，不是近期已磨损的审计/闸门/校验/预检/前后对比/回放/聚类形态（详见第 6 节自查）。

## 4. 深入论证（针对选中机会）

1. **目标用户**：重度使用 coding agent 做跨文件结构性重构的开发者与团队负责人。频次极高——几乎每天都在「用一句话给 agent 派重构活」。
2. **核心痛点（真实、高频、可付费）**：把结构性改动**用散文交给 agent**，天然丢失一批人本该拍板的决策（新名字？签名默认值？改动范围？传播到哪些调用点？），于是 agent 只能猜——少改、改错、过度改，人再花几轮纠偏。这段「人→agent 的意图交接」今天**零结构、零可复核**。团队为「让 agent 改得对」愿意付费（省的是最贵的返工与信任）。
3. **现有产品为什么没解决好**：
   - **IDE 重构（Rename Symbol / Change Signature 等）**确实是语义级的，但它们是**单点、在本 IDE 里由人手动执行**的，**不把多个结构意图组合成一份可复核、可交接的「改动谱」**，也**不产出可交给外部 coding agent 执行的可移植产物**。
   - **Zero** 用「换新语言 + 图优先」拿到语义级编辑，但迁移成本极高、只覆盖用 Zero 写的新代码。
   - **coding agent 自身**接收的是自然语言，歧义在输入端就已产生。
   - 缺的正是中间这层：**人在意图空间编排、agent 拿到无歧义语义清单去执行**的交接面。
4. **为什么适合做轻量 Demo**：改动谱的展开（哪些引用被触达、执行顺序、范围随参数变化）是**纯确定性的图遍历**，可用一份手工构造、可信的 mock 代码库 + 引擎完全复现，无需任何真实后端 / LLM / 外部 API。交互性强（增删操作、切换参数 → 实时重算），3 分钟内能让人看懂价值。

## 5. 不照抄声明（四项必填）

1. **创新切入点是什么**：一层**厂商中立、覆盖现有语言**的「语义改动谱」编排面——把「让 agent 改代码」从一句散文，升级成**人能编排、agent 能精确演奏**的结构化操作谱（typed semantic ops），并产出**可移植、机读的交付清单**。
2. **解决的具体问题 / 场景**：跨文件结构性重构中，「人→agent」的意图交接是散文、藏着未拍板的决策、不可复核，导致 agent 少改/错改/过度改与反复纠偏。
3. **相对被参考产品的增量价值（差异点）**：
   - vs **Zero**：不换语言、不搞图优先迁移；**回填到现有语言与现有 agent 工作流**，当下可用；治的是「人→agent 的写」（意图编排），Zero 治的是「编译器→agent 的读」（诊断/patch 原语）。
   - vs **IDE 重构**：把**多个语义操作组合成一份可复核、可交接的谱**，并导出**可给外部 coding agent 执行的可移植 manifest**；而非在本 IDE 里由人单点手动执行、无产物。
   - vs **coding agent 直接吃自然语言**：把歧义**在输入端消除**（每个操作的目标、范围、顺序都被解析成稳定符号 id），agent「零猜测」。
4. **为什么这不是照抄 Zero（本质区别）**：Zero 是一门**新系统语言 + 图优先编译器**，价值只对用 Zero 写的新代码生效，且 `patch` 是给 agent 用的 CLI 原语；编谱是**面向人的、语言中立的意图编排 UX**，不引入任何新语言、作用于**你现有的代码库**，产物是给 agent 的**改动谱**。我借的是 Zero 的**思想**（语义级、机读、少猜），不是它的**形态**（新语言/新编译器）。

## 6. 不确定性与风险

- **需求侧风险**：一部分开发者习惯「直接跟 agent 聊」，可能觉得「先编排再交接」多了一步；需要证明这一步省下的返工远大于成本（Demo 用「歧义消除计数 / 少猜点数」把收益显性化）。
- **落地 / 技术风险**：真实产品需要可靠的多语言语义索引（LSP/tree-sitter/自建图）与安全的语义级改写引擎，工程不轻——但这属于「真实产品的护城河」，Demo 阶段用确定性 mock 图即可讲清价值，不影响机会成立。
- **形态邻接风险（诚实自查）**：本机会与「闸口（08-16，agent 动作 blast-radius 预检）」「对表（08-08，指令契约 CI）」有**表层邻接**（都会显示「一个改动触达什么」）。**关键区别**：闸口/对表是**事后/被动**地审、检、门控 agent 的产出或行为；编谱是**事前/主动**地由人**编排意图本身**并产出交付物——核心体验是**创作/编排（authoring）**，不是审计/闸门/校验/前后对比/回放。Demo 会刻意弱化 blast-radius/门控叙事、强化「编排→展开→交付」的创作动线，以保持形态新鲜。
- **我可能判断错的地方**：也许未来 coding agent 的语义理解足够强，散文歧义被模型自身消化，这层编排面的价值被稀释；但即便如此，「人主动拍板结构决策 + 留下可复核的改动谱」在团队协作/合规/回溯上仍有独立价值。
