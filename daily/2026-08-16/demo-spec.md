# Demo 设计说明 — 2026-08-16

## 1. Demo 名称

**闸口 Zhākǒu · Sluice** —— Agent 动作策略的「爆炸半径」上线前预演台
（Blast-Radius Preflight for Agent Action Policies）

## 2. 一句话定位

上线前，先让你的护栏策略跑一遍一份真实感的「agent 拟执行动作」语料：哪些自动放行、哪些叫人复核、哪些一票否决，最坏能溜过去的不可逆动作有多大**爆炸半径**，还有多少动作落进没人管的**默认盲区**。

## 3. 目标用户

给 coding/ops agent 车队配了真实工具权限（shell / git / 文件系统 / 云 API / 数据库 / 支付 / 外发邮件 / 浏览器）、准备**上线或调整护栏策略**的平台工程 / SRE / 安全负责人。

## 4. 使用场景

「我要给 agent 开放 prod 权限了，先别急着上——把我这套护栏策略跑给一批典型动作看看：会不会自动放行了删库、退款、把 secret 外发这类不可逆动作？人审会不会一天几百条根本审不过来？有没有动作根本没规则命中、走了默认放行？调一版策略，再看爆炸半径缩到多小、人审负载变多少。」

## 5. Demo 策略分型（重要）

- 本机会属于：☑ **抽象 / 控制面 / 基础设施类产品**（agent 动作治理策略，无 UI 原型可直接点）
- 采用的演示方式：纯前端**「模拟体验 + 价值可视化」**
  - **可调策略台**（编辑护栏规则、人审预算、默认路径）＝把抽象的「策略」变成可操作对象；
  - **动作回放**（对 mock 语料逐条判决）＝脚本化重放核心工作流；
  - **爆炸半径 / 盲区可视化 + before/after 对比**＝直观展示增量价值。
- 演示的是**我们分析出的创新切入点**（设计期的策略预演 + 爆炸半径 what-if），**不是** Phinq（运行时守卫）的克隆。

## 6. 核心流程（用户 3 分钟内可完成）

1. **进入 · 策略台**：看到默认「均衡」策略与一份 12 条的 agent 拟执行动作语料，顶部大字给出当前策略的三个关键指标——自动放行的不可逆动作数、爆炸半径分、人审负载 vs 预算。
2. **回放 · 逐条判决**：切到「回放」，看引擎对每条动作给出 ✅放行 / 🙋叫人 / ⛔否决 的判决与**可解释理由**（命中了哪条规则）。危险的「自动放行了不可逆动作」被高亮标红。
3. **收紧 · 看爆炸半径缩小**：回策略台，一键切到「严格」预设或手动打开「不可逆动作强制人审」「prod 动作强制人审」「拦截 secret 外发」——回到「爆炸半径」页看 **before/after**：爆炸半径分下降、漏网不可逆动作归零、但人审负载上升（演示「安全 vs 告警疲劳」的真实权衡），并看到「盲区」里有几条动作其实没规则命中。

## 7. 页面结构（3 个主要页面 / Tab）

- **页面 1 · 策略台（Policy Desk）**：左侧护栏策略编辑器（3 个预设：宽松/均衡/严格 + 分类规则下拉 + 4 个全局开关 + 人审预算滑杆 + 默认路径三选一）；右侧实时「策略计分卡」（爆炸半径分、漏网不可逆数、人审负载/预算、盲区数）。改任何一项，右侧即时刷新。
- **页面 2 · 回放（Replay）**：动作语料表格，逐条显示 agent / 工具 / 目标范围（local/staging/prod/external）/ 可逆性 / 数据敏感度 / 意图，以及引擎判决（放行/叫人/否决）+ 理由 chips。顶部三态计数条；可筛选「只看漏网危险动作」。
- **页面 3 · 爆炸半径 & 盲区（Blast Radius & Gaps）**：上半部「爆炸半径矩阵」——把**自动放行**的动作按（可逆性 × 影响面）铺成风险面，红区即「上线后能自己炸的范围」；下半部 before/after 对比条（当前策略 vs 宽松基线）+「策略盲区」清单（无规则命中、走默认路径的动作）。

## 8. 关键交互

- **确定性护栏引擎**（`engine.ts`）：输入 `Policy + Action[]`，输出每条 `Verdict{ decision, reasons[], matchedRule }` 与聚合指标（爆炸半径分、漏网不可逆、人审负载、盲区）。全程纯函数、可解释、可复现。
- 预设一键切换（宽松/均衡/严格）＋ 单项开关/滑杆微调，所有视图**即时联动**刷新。
- 「只看危险漏网」筛选；每条判决可展开看命中理由。
- before/after 对比恒以「宽松基线」为参照，直观量化「我这版策略把爆炸半径压了多少、多花多少人审」。

## 9. 使用的 mock 数据

- `mock.ts`：
  - **动作语料**：12 条典型 agent 拟执行动作，覆盖 shell/git/fs/cloud/db/net/comms/payment 八类工具，范围含 local→prod→external，含若干高危不可逆项（`DROP TABLE` on prod、`rm -rf` 部署目录、退款 API、把含 PII 的表导出到外部、给全体用户群发邮件等）与若干安全项（读日志、跑单测、开 draft PR）。
  - **三套预设策略**（宽松/均衡/严格）与全局开关/预算的默认值。
  - 所有属性（可逆性、数据敏感度、影响面、基础风险分）均为**人工标注的 mock**，不接任何真实 agent trace / LLM 分类。
- 数据结构：`Action`、`Policy`、`Verdict`、`Scorecard`（详见 `src/types.ts`）。

## 10. 明确不做什么

- 不做登录 / 用户系统。
- 不接数据库 / 支付 / 外部私钥 / 真实 API / LLM / 真实 agent 运行时。
- 不做生产级后端；不做真实动作拦截（那是运行时守卫如 Phinq 的活）。
- 不声称 mock 的风险判定具备生产精度——它演示的是**策略预演的价值形态**，不是判定引擎本身。

## 11. 成功体验标准

- 用户 3 分钟内能说出：**它解决什么**（上线前看清 agent 护栏的爆炸半径与盲区）、**怎么用**（改策略→重放→看 before/after）、**增量在哪**（设计期 what-if + 厂商中立对比，区别于运行时守卫）。
- 用户能亲手把「严格」策略跑出来，看到**漏网不可逆动作从 N 降到 0**、同时**人审负载上升**，从而直观理解「安全 vs 告警疲劳」的权衡——这一「顿悟时刻」即成功。
