## 2. 候选机会（4 个，均为创新切入点而非照抄报告里的产品）

### 候选 A：环境体检台（RL/评测任务的「可解性 + reward-hack 风险」审计工作台）
- 创新切入点：把 GLM-5.3「judge agent 验证可解」的内部步骤**外化成一个独立产品**——烧 GPU 跑 RL 前，先对合成任务语料做「体检」：哪些被 judge 证实可解、哪些歧义/不可解、哪些存在 reward-hacking 漏洞（可被空跑/作弊拿分），并可视化预期 bench 增益。
- 目标用户 / 场景：做 agent 后训练/评测的模型团队、eval 平台工程师。
- 五维评分：痛点 4/5，机制新意 4/5，方向相关 5/5，一天可行性 4/5，启发价值 5/5 → 合计 **22/25**

### 候选 B：闸口 Zhákǒu（Agent 动作策略的「爆炸半径」上线前预演台）
- 创新切入点：不做 Phinq 那样的**运行时**守卫，而做**上线前的策略设计 + 爆炸半径推演**工作台。你编辑一套厂商中立的护栏策略（自然语言规则 + 人审预算 + 默认路径设定），对一份 mock 的「agent 拟执行动作」语料做**回放**，直接看到：哪些自动放行 / 哪些叫人复核 / 哪些一票否决（fail-closed），最坏能溜过去的不可逆动作有多大「爆炸半径」，以及有多少动作落进「无规则命中」的默认路径（策略盲区）。
- 目标用户 / 场景：给 agent 配了工具权限（shell/云 API/DB/支付/外发）、准备上线或调整护栏的平台/SRE/安全团队。
- 五维评分：痛点 5/5，机制新意 4/5，方向相关 5/5，一天可行性 5/5，启发价值 5/5 → 合计 **24/25**

### 候选 C：车队路由 · 成本悬崖推演台（agent fleet 的 model routing + 引入价 what-if）
- 创新切入点：面向 agent 车队，按步骤定义跨模型目录的路由规则，回放一份 mock 工作负载，可视化成本/质量/延迟，并特别推演「Gemini 引入价 2027 翻倍」这类**价格悬崖 what-if**。
- 目标用户 / 场景：跑 agent 车队、要控 $/token 的平台团队。
- 五维评分：痛点 4/5，机制新意 3/5，方向相关 4/5，一天可行性 4/5，启发价值 4/5 → 合计 **19/25**

### 候选 D：反问式决策预演台（2C · 非附和的决策 pre-mortem 伙伴）
- 创新切入点：一个「会反问、不附和」的决策预演伙伴，在你要拍板前先做 steelman 反方 + 逼出隐藏假设。
- 目标用户 / 场景：要独自做高风险决策、担心 AI 一味附和的个人。
- 五维评分：痛点 3/5，机制新意 3/5，方向相关 3/5，一天可行性 4/5，启发价值 3/5 → 合计 **16/25**

## 3. 最终选择

- 选中：**候选 B — 闸口 Zhákǒu（Agent 动作策略的爆炸半径上线前预演台）**，总分 **24/25**
- 为什么选它（相对其他候选的优势）：
  1. **痛点最硬且最切「高风险工具调用的控制面」这条 lab-focus 明列方向**：一旦 agent 有了 prod 权限，「上线前看不清爆炸半径」是所有团队的共同恐惧，比候选 A（受众更窄的模型团队）覆盖面更广。
  2. **可行性满分**：策略编辑 + 动作回放 + 三态路由（放行/叫人/否决）+ 爆炸半径/盲区可视化 + before-after，全部可用**确定性、可解释的前端引擎**跑通，不需要任何 LLM/后端。
  3. **差异化清晰、抗「照抄」质疑**：Phinq 是运行时守卫，我是设计期 what-if 模拟器 + 策略 linter，生命周期阶段不同、产品形态不同（详见第 5 节）。
  4. 相比候选 C（路由品类拥挤、机制新意仅 3）与候选 D（概念包装风险），B 在「新意 × 可行性 × 方向相关」三者上综合最优。

## 4. 深入论证（针对选中机会）

1. **目标用户**：给 coding/ops agent 车队配置了真实工具权限（shell、git、文件系统、云 API、数据库、支付、外发邮件、浏览器）的平台工程 / SRE / 安全负责人。
2. **核心痛点（真实、高频、可付费）**：agent 自主度越高，「它会不会自己干一件不可逆的蠢事」越是上线前的头号阻碍。现状是拍脑袋写一版护栏就上，出事才知道漏了；调策略像盲改——放太松出事故，放太严则**人审告警疲劳**，团队根本不知道自己策略的「爆炸半径」和「盲区」有多大。这是可以为「安全上线信心」付费的 B2B 痛点。
3. **现有产品为什么没解决好**：报告里的 Phinq/Coarena 都在**运行时/竞技场**侧发力——等 agent 真去跑了才拦或才评。**设计期**的「如果我这么配策略，会放行/拦下哪些动作、最坏爆炸半径多大」这个 what-if 问题，没有厂商中立、可回放、可对比的工具来回答。
4. **为什么适合做轻量 Demo**：整套价值可用「模拟体验 + 价值可视化」呈现——一份 mock 动作语料 + 一个确定性护栏引擎，用户 3 分钟内就能「改策略→重放→看爆炸半径缩小/人审负载变化」，完全不需要真实 agent 或后端。

## 5. 不照抄声明（四项必填）

1. **创新切入点是什么**：把 agent 动作治理从「运行时拦截」前移为「**上线前的策略设计 + 爆炸半径 what-if 预演**」——一个厂商中立、对任意 agent 动作日志都能跑的**设计期模拟器 + 策略 linter**。
2. **解决的具体问题 / 场景**：上线/调整护栏前，量化回答三件事——(a) 这套策略会自动放行哪些不可逆动作、最坏爆炸半径多大；(b) 人审负载是否超预算（告警疲劳 vs 漏网）；(c) 有多少动作落进「无规则命中」的默认路径（策略盲区）。
3. **相对被参考产品（Phinq）的增量价值（差异点）**：
   - Phinq = **运行时**执行边界守卫（fail-closed + 人审），作用在 agent 已经要动手的那一刻。
   - 闸口 = **设计期**的 what-if 模拟与对比：在部署前把策略跑给一份动作语料看，**可对比 before/after**、可看**覆盖盲区**、可调**人审预算**。它不拦真实动作，它帮你在出事前把策略调对。二者是同一问题在**不同生命周期阶段**的互补品，不是替代。
4. **为什么这不是照抄 Phinq（本质区别）**：Phinq 是「嵌进 agent 运行时、真刀真枪拦动作」的**内核/守卫**；闸口是「离线跑 mock 语料、给策略做体检和对比」的**设计工作台**。若用户想要运行时拦截，直接用 Phinq 即可——闸口提供的是 Phinq 给不了的「上线前先看清爆炸半径与盲区」的决策支持。二者产品形态、运行时机、交付物均不同，非克隆。

> 与本实验室 08-14「说戏 Shuōxì」的区别：那是**视频 agent 的改稿/导演层**（keep-vs-regenerate diff），本机会是**agent 动作治理的策略预演台**，领域、用户、引擎逻辑完全不同，仅都用到「before/after 对比」这一通用可视化手法。

## 6. 不确定性与风险

- **需求侧风险**【我的判断】：设计期 what-if 的付费意愿可能弱于运行时守卫（后者「不装就出事」更刚性）；需要证明「上线前预演」能真实减少事故/告警疲劳，否则会被当成「锦上添花」。
- **落地 / 技术风险**：真实产品的价值取决于**动作分类与可逆性判定的准确度**（本 Demo 用 mock 属性规避了这一最难环节）；真实场景里动作语料的获取（接 agent trace/审计日志）是工程门槛。
- **我可能判断错的地方**：也许运行时守卫厂商（如 Phinq）会顺手把「策略预演」做成一个 tab，从而不构成独立产品；若如此，我的差异化窗口会变窄——但「厂商中立、可对比多家 agent」仍是我的立足点。
- **Demo 边界诚实声明**：Demo 的护栏引擎是**确定性脚本**，非真实 LLM 风险分类；动作语料与可逆性/数据敏感度均为 mock；它演示的是「策略预演」这一创新切入点的价值形态，不代表生产级判定精度。
