# Demo 设计说明 — 2026-07-26

## 1. Demo 名称
岔口 Forkpoint

## 2. 一句话定位
面向"可续跑 / 可分叉 agent 会话"（OpenComputer 式事件日志）的**时间旅行归因 + 纠偏分叉调试台**：给一次跑了几十步、给出"看起来对但错"结论的 agent 会话，自动**揪出那 1 个决定错误结论的折返步**，并支持"从该步 fork 一条纠偏轨迹 + 确定性重放"，用 before/after 证明"修这一步→结论真的翻转"。

## 3. 目标用户
在 OpenComputer / 托管 agent 运行时上跑**长链路、有状态**自治 agent 的应用团队、平台工程与独立开发者。

## 4. 使用场景
一个数据分析 agent 被要求"判断改版后新用户 D7 留存是否显著提升、是否全量上线"，跑了 9 步给出"提升 +8pp，建议全量上线"——**看起来专业、其实错了**（它把 D1 留存当成了 D7）。人要逐步读 9 步日志才可能发现，且不敢确定是哪步导致。岔口把这件事变成"跳到第 5 步 → 从这步纠偏重放 → 结论翻转为不上线"。

## 5. Demo 策略分型（重要）

- 本机会属于：☑ 抽象 / CLI / API / 基础设施类产品（agent 运行时之上的归因决策层）
- 采用的演示方式：纯前端"**模拟体验 + 价值可视化**"——
  - **网页版会话事件日志回放**（脚本化重放一次 9 步 agent 会话）；
  - **交互式纠偏分叉重放**（选一步 → 施加纠偏动作 → 下游确定性重放 + 结论翻转）；
  - **before / after 对比**（错误轨迹 vs 纠偏轨迹的关键数字 + 价值指标）。
- 演示的是**我们的创新切入点**（折返步定位 + 因果确认 + 纠偏重放证据），不是 OpenComputer（运行时）的克隆，也不是只读 trace 查看器。

## 6. 核心流程（3 分钟内可完成）
1. 进入「会话回放」：看到任务目标（D7 留存、阈值 p<0.05）、9 步会话时间线、最终**红色错误结论**"建议全量上线"。点"自动定位折返步"→ 第 5 步被标红（选错了指标列 `retained`(=D1) 而非 `retained_d7`）。
2. 进「岔口纠偏」：先在**第 3 步**（一个真实存在但无害的异常：丢了 2.4% 脏数据）尝试 fork → 下游重放 → **结论不变**（仍"上线"）→ 提示"非折返点：修它不改结论"。再在**第 5 步** fork（改用 `retained_d7`）→ 下游重放 → **结论翻转**为"D7 无显著提升、不建议全量上线"→ 提示"命中折返点"。
3. 看 before/after 对比与价值指标卡：指标列 `retained`→`retained_d7`、lift +8pp→−1pp、p 0.008→0.62、显著 是→否、结论 上线→不上线；折返步 5/9、被污染步 4、少读步数 8、避免的错误上线 ×1。
4. （可选）进「归因台账」：看每步 × 不变量检查表，理解"折返步 = 最早'单独修它就能让结论翻转'的步"，以及岔口与 OpenComputer 续跑/分叉的分工。

## 7. 页面结构（<= 3 个主要页面 / Tab）
- 页面 1「会话回放 Replay」：任务目标卡 + 9 步时间线（绿/黄/红着色，可点选）+ 选中步详情（动作/读入/写出状态/命中的不变量）+ 最终结论条 + "自动定位折返步"。
- 页面 2「岔口纠偏 Forkpoint」：选择 fork 步 + 可用纠偏动作 + "分叉并重放"（下游即时重新着色/更新）+ 命中/未命中折返点提示 + before/after 关键数字对比 + 价值指标卡。
- 页面 3「归因台账 Ledger」：每步 × 不变量检查表（期望/实际/是否违反/是否传导到结论）+ 折返判定解释 + "如果没有 Forkpoint"叙事 + "岔口(方向盘) ↔ OpenComputer(马达)"分工说明。

## 8. 关键交互
- 时间线**点选任一步** → 右侧显示该步状态与不变量检查。
- "**自动定位折返步**"：高亮红色折返步（第 5 步）。
- "**从此处分叉并重放**"：选步 + 选该步的纠偏动作 → 下游步骤**确定性重放**并重新着色，结论条更新，弹出"命中/未命中折返点"。
- **判别力演示**：在非因果步（第 3 步）fork → 结论不变 → 明确提示"非折返"；在折返步（第 5 步）fork → 结论翻转 → "命中"。
- before/after 双列对比 + 价值指标卡随重放更新。

## 9. 使用的 mock 数据
（全部为 mock / 演示用，不接真实后端、数据库、外部 API，也不做真实统计推断）
- 一条 mock 会话事件日志：9 步，每步含 `action / 摘要 / 读入 / 写出状态(kv) / 命中的不变量检查`。
- 一份 mock 汇总统计（演示用、非真实）：D1 留存(`retained`) control 33% / redesign 41%（+8pp，p=0.008）；D7 留存(`retained_d7`) control 25% / redesign 24%（−1pp，p=0.62）。改版只提升了 D1（疑似新鲜感效应），未提升 D7 —— 这正是"选错指标列"导致错误结论的根因。
- 目标不变量集合：指标列须=`retained_d7`、分母须为窗口内注册用户、窗口边界一致、显著性阈值 p<0.05、样本量充足。
- 一个**确定性引擎** `engine.ts`：输入 = 每步决策（如 `metricColumn`、`dropRule`），输出 = 逐步状态 + 不变量违反 + 最终结论。"折返步"由引擎**可复算地**判定：最早"单独修正该步就能让最终结论翻转为正确结论"的步。

## 10. 明确不做什么
- 不做登录 / 用户系统
- 不接数据库 / 支付 / 外部私钥 / 真实 API / 真实 agent 运行时 / 真实统计推断
- 不做生产级后端
- 不做真实会话采集（真实版才接 OpenComputer 事件日志）

## 11. 成功体验标准
- 用户 3 分钟内能说出："它解决什么问题（长链路 agent 出错时定位那 1 步坏步 + 证明修它有用）、怎么用（回放→在折返步 fork 重放→结论翻转）、增量在哪（比只读 trace 多了因果确认与纠偏证据；比运行时多了'该续哪一步'的决策）"。
- 用户能亲手体验"在非折返步 fork 结论不变 / 在折返步 fork 结论翻转"，直观感到工具**有判别力**。
