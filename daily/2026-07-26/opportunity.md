## 2. 候选机会（4 个，均为创新切入点而非照抄）

### 候选 A：岔口 Forkpoint —— 面向可续跑/可分叉 agent 会话的「时间旅行归因 + 纠偏分叉」调试台
- 创新切入点：把 OpenComputer 刚普及的"事件日志断点续跑 + checkpoint 分叉"原语，做成一个**归因决策层**：给定一次 agent 会话（几十步）+ 任务目标 + 每步产出的状态，自动**定位那一个"折返步"**（第一处"违反目标不变量、且该违反一路传导到最终错误结论"的步），支持**从该步 fork 一条纠偏轨迹并确定性重放**，用 before/after 证明"改这一步→结论真的变对"。核心是"**把 18 步里那 1 步坏的揪出来 + 证明修它有用**"，而不是又一个只读的 trace 查看器。
- 目标用户 / 场景：任何在 OpenComputer/托管 agent 运行时上跑**长链路、有状态 agent** 的团队与独立开发者——agent 给了个"看起来对但错"的结论/产物，人要花很久逐步读日志才找到哪步坏了，且找到也不敢确定"是不是这步导致的"。
- 五维评分：痛点 5/5，机制新意 4/5，AI 核心度 5/5，一天可行性 4/5，启发价值 5/5 → 合计 **23/25**

### 候选 B：复真 Veritas —— agent 自写集成的「语义现实校验」harness（riding Velane）
- 创新切入点：Velane 让 agent 自写自测集成代码；我补上它**自评作业**的盲区——不信任 agent 自己写的测试，而是拿它生成的 snippet **对齐外部服务的已知语义契约**（Stripe 金额单位/幂等键、分页、软删除、限流语义等一个策展的"语义陷阱库"），专抓"编译过、自测过、但对真实服务语义错"的一类静默 bug，发布前给出差异清单。
- 目标用户 / 场景：用 Velane 式"agent 自建集成"的团队，怕 agent 误解第三方 API 语义而静默上线错代码。
- 五维评分：痛点 4/5，机制新意 4/5，AI 核心度 4/5，一天可行性 3/5，启发价值 4/5 → 合计 **19/25**
- 未选理由：价值真实，但"语义陷阱库"的可信度高度依赖策展质量，Demo 里易显得手造；且与主选相比，痛点更"前瞻"（依赖 agent 自建集成已大规模发生）。

### 候选 C：择优台 GroupPick-Dev —— 并行编码 agent 的「best-of-N 结果裁决」（riding ADE）
- 创新切入点：ADE 让你并排跑 N 个编码 agent；下游真问题是"N 份候选解怎么快选一份最优"。做一个**基于同一验收标准 + 一致/分歧分析**的 bake-off 视图：哪些候选过同一组验收、谁 diff 最小最稳、谁走了高风险路子、N 份在哪里"一致（高置信）"vs"分歧（需你判断）"，给推荐并说明理由。

- 目标用户 / 场景：管理慢性/多头健康关切、常在 12 分钟问诊里遗忘/漏问的普通消费者。
- 五维评分：痛点 4/5，机制新意 3/5，AI 核心度 3/5，一天可行性 4/5，启发价值 3/5 → 合计 **17/25**
- 未选理由：2C 今日信号薄、"备诊/复诊清单"类工具已多、AI 核心度偏软；医疗归因（"有没有用"）涉因果，纯前端 Demo 难诚实呈现。达门槛但非最优。

## 3. 最终选择

- 选中：**候选 A —— 岔口 Forkpoint**，总分 **23/25**
- 为什么选它（相对其他候选的优势）：
  1. **正踩今日最强原语的空白**：OpenComputer（16/18，今日并列最高）第一次把"事件日志断点续跑 + checkpoint 分叉"做成普及能力——但报告只讲"能续跑"，没人讲"该从哪一步续、续了怎么证明变对"。这是**能力刚就位、产品还空着**的最锋利切口。
  2. **诚实、反自嗨**：不做又一个只读 trace 查看器（那类已拥挤），而是做"**揪出那 1 步 + 证明修它有用**"的写回闭环——且刻意展示"不是每个异常都是元凶"（在错的步 fork 结论不变），证明工具是**有判别力**的，不是见异常就报警。
  3. **刻意避开过热家族**：A 完全不碰授权/审批/审计/溯源/信任（我 07-21..07-24 已反复警惕的治理邻域），也不是 07-24 榫卯的"跨 agent 数据形状契约"——A 是**单会话、事后、执行轨迹的根因+纠偏**，家族全新。
  4. **可视化增量极清晰**：时间线回放 + 拖动折返点 + 下游重放着色 + before/after 结论对比，3 分钟讲清"从读 18 步 → 跳到 1 步、并证明修它结论翻转"。

## 4. 深入论证（针对选中机会）

1. 目标用户：在托管/开源 agent 运行时（OpenComputer 式）上跑**长链路、有状态**自治 agent 的应用团队、平台工程、独立开发者。他们的会话动辄几十步、常驻数小时，人无法全程盯，且**"错得不报错"**（plausible-but-wrong）是最难查的一类。
2. 核心痛点（真实、高频、可付费）：
   - "它给了个看起来合理的结论，但错了——**哪一步坏的？**"逐步读日志成本极高；
   - "我以为是第 3 步的小异常，改了没用——**到底是不是这步导致的？**"缺乏因果确认；
   - "改完怎么知道真变对？"——没有"从那步 fork 重放、拿到正确结论"的证据闭环；
   - 结果：要么放弃归因、重跑整条链（贵、且可能再错），要么误信错误结论**把坏决策上线**。这些都是真金白银，团队愿为"少读 200 步、少上线一次坏结果"付费。
3. 现有产品为什么没解决好：现有 trace/observability（LangSmith/Langfuse 类）优化的是**只读记录与检索**；OpenComputer 优化的是**运行时续跑能力**；二者都不做"**替你定位那一个决定错误结论的步 + 从该步 fork 纠偏并证明**"。归因（哪步）+ 因果确认（是不是这步）+ 纠偏证据（修了变对）这三件事绑成一次操作——正是岔口的位置，也是"续跑/分叉原语"刚刚使其变得可做的层。
4. 为什么适合做轻量 Demo：整套逻辑是**确定性的**——给定一条 mock 会话事件日志（每步读/写状态）、任务目标与一组"目标不变量"，引擎即可算出每步是否违反不变量、违反是否传导到最终结论（→定位折返步），并对"从某步 fork + 施加纠偏"做确定性下游重放。无需真实 agent、无需 GPU/后端/外部 API，用 mock 日志 + 一个可复算引擎即可"模拟体验 + 价值可视化"，一天内做出可点击三页原型。

## 5. 不照抄声明（四项必填）

1. **创新切入点是什么**：把 OpenComputer 的"事件日志断点续跑 + checkpoint 分叉"从**运行时能力**，做成**归因决策产品**：自动定位一次 agent 会话里"决定了错误结论的那 1 个折返步"，并支持"从该步 fork 纠偏 + 确定性重放"来**证明**修它能让结论翻转。核心是**"揪出坏步 + 因果确认 + 纠偏证据"**的写回闭环，且**有判别力**（在非因果步 fork 结论不变）。
2. **解决的具体问题 / 场景**：长链路 agent 给出"看起来对但错"的结论时，人要花很久逐步读日志找哪步坏、找到也不敢确定因果、改完无法证明变对——常导致误信错误结论把坏决策上线。
3. **相对被参考产品的增量价值（差异点）**：OpenComputer 让"回到某步续跑"**可行**（马达）；岔口告诉你"**该回到哪一步、为什么是这步、回去修了结论真的变对**"（方向盘 + 证据）。岔口的输出（折返步定位 + 纠偏点 + 重放证据）正是喂给 OpenComputer"从 seq N 续跑/分叉"的**决策输入**——互补而非替代。相对只读 trace 工具，增量是从"看得到"升级为"**定位 + 因果确认 + 纠偏证据**"。
4. **为什么这不是照抄 OpenComputer（本质区别）**：OpenComputer 是**运行时**（造 VM、存事件日志、提供从任意 seq 续跑/分叉的能力，本身不判断"哪步该修"）；岔口**不造运行时、不跑真 agent**，只在其之上做**归因与纠偏决策**（定位折返步、确定性重放对比、证明因果）。二者位于价值链不同环节：一个"让续跑/分叉成为可能"，一个"告诉你该续/分叉哪一处并证明有用"。同时它**不是** 07-24 榫卯（那是跨 agent 数据形状契约的**写入时预防**；岔口是单会话执行轨迹的**事后根因+纠偏**），也**不是**只读 trace 查看器。

## 6. 不确定性与风险

- 需求侧风险：目标用户偏"已在跑长链路有状态 agent"的开发者/平台向，非大众高频；市场需先普及"agent 可续跑/可分叉"的心智（OpenComputer 这类刚起量），认知曲线存在。
- 竞争风险：trace/observability 赛道有 LangSmith/Langfuse 等；岔口的护城河在"**折返步定位（因果传导判定）+ 纠偏重放证据**"这套决策逻辑与体验，需持续把"定位准确率 + 纠偏可信度"做成壁垒，否则易被 trace 工具顺手加个"跳转到可疑步"覆盖。
- 落地 / 技术风险：真实版要读会话事件日志并对"目标不变量/违反是否传导到结论"做可靠推断——真实归因质量是产品成败关键；Demo 用确定性 mock 引擎规避，但真实世界的因果判定远比 mock 复杂（多因、隐性依赖）。
- 我可能判断错的地方：也许多数团队遇到 agent 出错宁可"重跑一遍"而非归因（尤其单次很便宜时）；若运行时厂商把"标记可疑步 + 一键续跑"原生化，中间层价值被削弱。我在 Demo 里正面回应：**重跑不定位=可能再错 + 贵**，而岔口给的是"少读 N 步 + 因果确认 + 一次改对"的确定性证据。

## 7. 门槛结论

- 最高分：**23/25**（候选 A 岔口 Forkpoint）
- 是否达到 16/25 门槛：**是**
- 结论：**进入 Demo 开发**（Loop 2–5）。策略分型：抽象 / 基础设施类 → 采用纯前端「模拟体验 + 价值可视化」（会话回放时间线 + 折返点定位 + 纠偏分叉重放 + before/after 对比）。
