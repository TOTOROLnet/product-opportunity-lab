## 1. 报告事实 vs 我的独立判断

| 维度 | 报告怎么说（参考资料） | 我作为创业者的独立判断 |
| --- | --- | --- |
| 便宜三倍的意义 | V4-Flash 输出价约为 V4-Pro 的 1/3，「换个模型 ID 就享受成本红利」 | **我强烈质疑「换个 ID 就享受」这句话。** $/token 是「表面单价」，agent 车队真正付的是「每个**成功完成**的任务」的钱。换更便宜的模型往往会改变每任务的步数、重试、工具调用失败率与成功率——**单位 token 便宜 ≠ 单位任务便宜，某些工作负载甚至会更贵**。 |
| 基准分数 | 官方自评在 Terminal-Bench/DeepSWE/Toolathlon 上反超自家更大模型 | 报告自己也承认这是**未公开 harness 的厂商自评、无第三方复现**。榜单分数迁移不到你的车队：你的 prompt/scaffold/任务分布/缓存命中率与厂商 harness 都不同。**能用来做迁移决策的只有「你自己的历史 trace 在两个模型上的重放结果」**，不是榜单，也不是单价。 |
| 缓存命中价 | $0.0028 命中价（比未命中便宜 50×） | 命中价只有在**高缓存命中**时才拿得到。工具调用方差大的 agent 工作负载命中率低，有效输入单价更接近未命中价。用命中价估算长跑成本会系统性低估。 |
| 并发 2500 | 并发上限是 Pro 的 5 倍，利好规模化 | 并发只有在你**被并发卡住**时才值钱；对成功率/步数没帮助。它是一个「上限」，不是「省钱」。 |
| 2C 机会 | 短信助理 / 实时反馈是关注方向，但今日无新达标产品 | 认同。**今日报告确实没有新的 2C 信号**，硬凑一个 2C 反而违背客观性；而这些 2C 方向（应承/知时类）我在实验室里已评估过并判为拥挤。今天诚实地走技术向。 |

（我认同报告「前沿竞争转向单位成本/并发/agentic 后训练」这条主线；但我**明确反对**由此推出的「换个 ID 就享受成本红利」的乐观结论——这正是我要做的产品要攻的靶心。）

## 2. 候选机会（至少 3 个，均为创新切入点而非照抄）

### 候选 A：换挡 Downshift —— 模型迁移的「按成功任务计价」离线复盘台
- 创新切入点：把「该不该换更便宜的模型」这个决策，从**看单价 / 看榜单**，改成**用你自己的历史 agent trace 在候选模型上重放**，算出真正决定成败的两个指标：**每个成功任务的成本**（= 每任务成本 ÷ 成功率）与**成功率变化**，再给一个可执行的裁决（值得换 / 有条件换 / 先修再换 / 别换）。核心洞见：**单位 token 便宜可能让单位任务更贵，甚至掉成功率导致根本不能上线。**
- 目标用户 / 场景：跑 Codex 类 / 多 agent 车队的技术团队，面对「DeepSeek/GLM/Kimi 又便宜了，要不要换」的高频决策。
- 五维评分：痛点 5/5，机制新意 4/5，方向相关(AI 核心) 5/5，一天可行性 5/5，启发价值 5/5 → 合计 **24/25**（见 §3 我对机制新意做了诚实下调）

### 候选 B：迁前体检 DropInDoubt —— 「换个模型 ID」不是无痛的：行为契约 diff
- 创新切入点：换模型 ID 会静默改变**行为契约**——工具调用格式遵从度、JSON 严格性、拒答率、啰嗦度（吃输出成本）、指令遵从。把同一批 prompt 在新旧模型上重放，**diff 行为**（不是比分数），暴露换 ID 后会悄悄断掉你 agent 的地方。
- 目标用户 / 场景：准备切模型、但被工具调用解析/拒答率突变坑过的团队。
- 五维评分：痛点 4/5，机制新意 3/5，方向相关 5/5，一天可行性 4/5，启发价值 4/5 → 合计 **20/25**

### 候选 C：榜外 OffBench —— 厂商 agentic 基准的「到不了你车队」拆解器
- 创新切入点：报告点名「未公开 harness 自评」。给定一条厂商基准宣称，拆解它迁移到你车队的落差：harness 差异、scaffold/prompt 差异、任务分布错配、缓存命中假设、并发限流现实，输出「这个分数你能拿到几成」。
- 目标用户 / 场景：技术选型时被榜单牵着走的团队 / 决策者。
- 五维评分：痛点 3/5，机制新意 3/5，方向相关 5/5，一天可行性 3/5，启发价值 4/5 → 合计 **18/25**

### 候选 D：应承 Keeper —— 短信助理里的承诺/待办账本（2C，无当日新信号）
- 创新切入点：从消息流里抽取「我答应过的事」，形成可核对的承诺账本。
- 说明：这依赖 08-01 的 Pally/Bo AI 信号，**本轮报告无任何新增 2C 证据**；且该方向与实验室既有的「知时（proactive recall）」高度邻近，此前已评估为拥挤。硬做属于违背客观性。
- 五维评分：痛点 4/5，机制新意 2/5，方向相关 4/5，一天可行性 4/5，启发价值 2/5 → 合计 **16/25**

## 3. 最终选择

- 选中：**候选 A — 换挡 Downshift**，总分 **22/25**（诚实修正后）
- 评分诚实说明：初评 24，我把「机制新意」从 5 下调到 **3**——因为「厂商话术 vs 诚实重算 → 裁决」这个**结构**与本实验室 08-01 的 **风洞 WindTunnel** 相似；再把「启发价值」保持 5、其余 5/5/5，最终 **22/25**。我认为它仍是今天最诚实、最贴合报告唯一新信号的机会。
- 为什么选它（相对其他候选）：
  - 相对 B（行为契约 diff）：B 只讲「会不会断」，A 直接回答老板真正问的那句「换了到底省不省钱、掉不掉成功率」，决策价值更高、更硬核。
  - 相对 C（榜单拆解）：C 停留在「为什么榜单不可信」，A 更进一步给出「那就用你自己的 trace 重放算钱」的替代动作，更可落地、Demo 更具体。
  - 相对 D（2C 承诺账本）：今日报告无新 2C 信号，硬凑违背客观性；且 D 与既有「知时」邻近。诚实地不选。

## 4. 深入论证（针对选中机会）

1. 目标用户：运营 agent 车队 / Coding agent 流水线的技术负责人、平台/基础设施工程师、为 LLM 账单负责的人。
2. 核心痛点（真实、高频、可付费）：模型价格战每周都在打（DeepSeek、GLM、Kimi 轮流降价），"要不要换"是**高频、直接烧钱**的决策；今天最常见的错误就是**看单价拍板**（报告还在推「换个 ID 就享受」）。换错的代价是：账单没降甚至升、成功率悄悄掉、线上事故。
3. 现有产品为什么没解决好：模型厂商给的是**单价表 + 自评榜单**（利益驱动，报喜）；LLM 网关/可观测工具（Helicone、LangSmith 之类）擅长**事后**记账与 trace，但不回答「**换到 B 会怎样**」这个**反事实**问题——没有把你的 trace 重放到候选模型、用「每成功任务成本 + 成功率底线」给裁决。这中间是空的。
4. 为什么适合做轻量 Demo：这是一个**确定性计算 + 价值可视化**问题。用 mock 的车队 trace 汇总 + 两个模型的价目表与重放行为，就能算出「表面单价 vs 诚实每成功任务成本」的强烈反差，并用裁决卡 + 盈亏平衡滑杆讲清方法论，纯前端即可，无需真跑模型。

## 5. 不照抄声明（四项必填）

1. 创新切入点是什么：**用你自己的历史 agent trace 重放，按「每个成功任务的成本」和「成功率是否守住产品底线」来做模型迁移决策**，而不是按 $/token 单价或厂商榜单。核心公式 `每成功任务成本 = 每任务成本 ÷ 成功率`，把「成本」和「能力」耦合进同一个数。
2. 解决的具体问题 / 场景：面对 DeepSeek-V4-Flash 这类「便宜三倍」的新模型，一键回答「我的车队换过去，到底省不省钱、掉不掉成功率、能不能上线」，并给出「值得换 / 有条件换 / 先修再换 / 别换」的可执行裁决与补救项。
3. 相对被参考产品的增量价值（差异点）：DeepSeek（被参考产品）卖的是**更便宜的单价 + 自评榜单**；换挡卖的是**买方视角、厂商中立的「每成功任务成本」真相**——它可能告诉你「这个模型对你的语音 agent 反而贵 35%，别换」，这是任何模型厂商都不会替你算的。
4. 为什么这不是照抄 DeepSeek（本质区别）：DeepSeek 是被评估的**对象（一个模型）**；换挡是评估**这个对象值不值得换的决策工具**，立场相反（厂商报喜 vs 买方求真）、指标相反（$/token vs $/成功任务）、动作相反（发布模型 vs 决定要不要迁移），自身**不训练、不托管任何模型**。
   - **与实验室内既有产品的区分（防止内部克隆）**：
     - 与 **风洞 WindTunnel（08-01）** 的区别：风洞评估的是**执行运行时（WASM 沙箱）**，用阿姆达尔式「工具分类 → 成本地板」算一个**成本倍率**，**完全不碰任务成功率**；换挡评估的是**模型**，用**trace 重放**算**每成功任务成本 + 成功率变化**，核心命题是「**价格×能力耦合**」——便宜的 token 可能压低成功率/抬高步数从而每成功任务更贵。对象不同、指标不同、暴露的失败模式不同。
     - 与 **值当 Worthwhile（07-14）** 的区别：值当做的是**花费归因/规划**（agent 作为付费主体，把钱摊到动作/价值上）；换挡做的是**A→B 二选一的迁移裁决**。
     - 与 **步账（07-28 被否）** 的区别：步账是**运行时按步动态路由**；换挡是**离线一次性迁移决策**（该不该把整个车队从 A 换到 B）。

## 6. 不确定性与风险

- 需求侧风险：团队可能没有系统化的 trace 记录，无法直接重放（缓解：先支持从网关日志/OTel 导入；Demo 里用 mock 汇总演示方法论）。
- 落地 / 技术风险：真实产品需要在候选模型上**真跑重放**才能拿到 B 的成功率/步数，成本与工程量不小（Demo 用 mock 行为参数规避，且明确标注这是「方法论演示」而非真实跑分）。成功率的判定（哪算成功）本身需要每个团队定义评测函数——这是真实产品的关键难点。
- 我可能判断错的地方：(a) 对很多工作负载，DeepSeek 便宜到「即使成功率掉几个点仍然每成功任务更便宜」——那「先算清楚」的价值会被稀释成「基本都能换」，产品沦为确认器；我在 Demo 里用「实时语音 agent」这个**诚实反例**（表面 -25%、实际 +35%）证明「一定要算」的必要性并不总成立于所有场景，但**足够常见到值得一算**。(b) 机制上与风洞相似，存在「实验室内自我重复」的观感风险——我已在 §5 明确对象/指标/失败模式三重差异，并把机制新意分诚实下调。
