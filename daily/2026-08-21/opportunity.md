## 2. 候选机会（至少 3 个，均为创新切入点而非照抄）

### 候选 A：留痕 Liúhén — Agent 上下文压缩(compaction)的「折叠差异 + 保命清单」审计台
- 创新切入点：把「一次压缩事件」变成可审计的**折叠差异（fold-diff）**：压缩前的上下文窗口 vs 压缩后的摘要，逐条给被丢弃/被有损压缩的内容**分类 + 风险标注**（用户硬约束 / 已定决策 / 文件引用 / 踩坑经验 / 待办 / 闲聊），并让用户维护一份**「保命清单」（pin）**，规定哪些内容压缩时必须保留；再用**回放**证明：这条真实轨迹在第 N 步跑偏，正是因为第 N-1 步的压缩丢了约束 X，把 X 钉住后跑偏消失。
- 目标用户 / 场景：跑长程 Agent 的开发者 / Agent 平台团队（含混元这类做 Agent/API 的一方）——一次几十上百步的编码/研究/运维 Agent 任务，中途必然触发压缩。
- 五维评分：痛点 4/5，机制新意 5/5，AI 核心 5/5，一天可行性 5/5，启发价值 5/5 → 合计 **24/25**

### 候选 B：连戏 Liánxì — 并行 Agent 团队多模态成片的「连续性合约 + 走样雷达」
- 创新切入点：不做视频生成本身，做「并行 Agent 团队」创作里最难的**跨镜头一致性**：把角色/服装/调色/世界观设成一份所有并行 Agent 都必须遵守的**连续性合约（story bible）**，逐镜检测走样（角色夹克变色、道具凭空出现、光线不接），并给「走样雷达」。
- 目标用户 / 场景：短剧/电商/品牌创作者与工作室。
- 五维评分：痛点 4/5，机制新意 4/5，AI 核心 4/5，一天可行性 4/5，启发价值 4/5 → 合计 **20/25**

### 候选 C：可读 Kědú — 让你的产品/API「被 Agent 用得对」的 Agent 体验(AX)审计台
- 创新切入点：大家都在抢着加 MCP 让 Agent 能消费自己的产品，但没人检查「Agent 到底能不能用对」。模拟多个 Agent 拿真实 job 去调你的 API/文档/MCP manifest，定位它们在哪里踩坑（参数歧义、缺样例、错误码语义不清、鉴权说不清），给「Agent 可用性评分」+ 按「能解锁多少 Agent 任务」排序的修复建议。
- 目标用户 / 场景：想让产品「被 Agent 用」的 API/工具/SaaS 团队。
- 五维评分：痛点 4/5，机制新意 4/5，AI 核心 4/5，一天可行性 5/5，启发价值 4/5 → 合计 **21/25**

## 3. 最终选择

- 选中：**候选 A — 留痕 Liúhén**，总分 **24/25**
- 为什么选它（相对其他候选的优势）：
  1. **押在当天最新、最具体、且无买方侧产品的信号上**：compaction 今天刚被 Grok 4.6 做成一等特性，报告也点名它是可迁移方向，但市面（含报告里所有产品）**没有一个是站在压缩之上、替使用方做审计与控制**的——这是干净的空位。
  2. **痛点机制性、厂商中立**：丢约束/丢决策是压缩机制本身带来的新失败模式，换更强模型也治不好，且对所有做压缩的模型/框架普遍存在 → 天然厂商中立的第三方层。
  3. **可视化增量极强**：折叠差异（before/after）、风险标注、保命清单、跑偏回放，全是「一屏看懂增量」的强演示素材，一天可做出高信服度的纯前端模拟。
  4. B 与本实验室 08-14「说戏」相邻、C 与 08-08/08-09 的工具面体检相邻，A 在「压缩这一步」的切口更新、更少重复（见第 5 节与历史选题的区分）。

## 4. 深入论证（针对选中机会）

1. 目标用户：跑长程（数十至上百步）Agent 的开发者、Agent 平台/框架团队、以及做 Agent/API 的模型厂商侧团队（报告明确点名混元一类）。
2. 核心痛点（真实、高频、可付费）：长任务必然触发上下文压缩；压缩是**静默**的——你不知道它扔了哪条硬约束/已定决策，直到 Agent 几十步后「忘了自己答应过什么」而跑偏，代价是整段返工的 token 与时间。团队愿意为「少一次大返工」付费。
3. 现有产品为什么没解决好：
   - 模型/厂商（Grok 4.6 等）**产出**压缩，是被审计方，不会自曝「我扔了什么、风险多大」；
   - 通用 LLM 可观测性（Langfuse/Helicone 类）记录 trace 与 token，但**不专门对压缩这一步做 before/after 差异、不给丢弃项分类与风险标注、更没有保命清单这种控制面**；
   - 结果是：压缩=黑盒，使用方只能事后猜「它是不是又忘了」。
4. 为什么适合做轻量 Demo：核心是一个**确定性、可解释的模拟引擎**——给定一条 mock 轨迹与一份保命清单，就能算出每次压缩保留/丢弃了什么、风险分多少、是否触发已知跑偏，并回放 before/after。无需真实模型、无需后端，纯前端可完整呈现「解决什么 / 怎么用 / 增量在哪」。

## 5. 不照抄声明（四项必填）

1. **创新切入点是什么**：站在「上下文压缩」这一步之上，做**买方侧**的折叠差异审计 + 风险分类 + 保命清单控制 + 跑偏因果回放。把压缩从「静默的降本特性」变成「可读、可控、可问责的控制面」。
2. **解决的具体问题 / 场景**：长程 Agent 因压缩静默丢弃硬约束/已定决策而在几十步后跑偏、造成整段返工——事前看不见、事后难归因。
3. **相对被参考产品的增量价值（差异点）**：
   - 相对 **Grok 4.6**：它是**产出压缩的一方（模型）**；留痕是**站在其之上、厂商中立、替使用方审计与控制压缩**的第三方层，被压缩对象与审计者角色相反。
   - 相对**通用 LLM 可观测性**：不是又一个 trace/token 看板；专门给「压缩事件」做 before/after 逐项差异、丢弃项分类与风险标注，并提供保命清单这一**控制**动作（不只是观测）。
   - 相对 **Berd/ACP、Prized**：它们分别解决客户端解耦与执行期安全护栏；留痕解决的是**上下文层的信息保全**，正交互补。
4. **为什么这不是照抄 X（本质区别）**：留痕不生成、不托管模型，也不是记账/审批门；它唯一的产品是「让压缩这一步变得可审计、可干预」。与本实验室历史选题也刻意区分——**07-31「忆证」**是在**记忆库的回忆时刻**做信任/矛盾闸（对象是持久记忆库、动作是给召回项打信任分）；**08-07「归位」**是**复跑前**的世界状态重校；留痕针对的是**单次长运行内、压缩/摘要这一步**的有损折叠（对象是当下上下文窗口、动作是钉住条目对抗压缩），时机、对象、控制动作都不同，非同一产品的换皮。

## 6. 不确定性与风险

- 需求侧风险：compaction 是**当天**才被做成一等特性，市场教育尚早——今天最痛的是长程 Agent 的重度用户与平台方，普及需要时间（因此痛点给 4 而非 5）。
- 落地 / 技术风险：真实产品需要接入各家「压缩前/后」的上下文快照，而多数厂商今天并不暴露压缩中间态；真实版可能要靠自建压缩中间件或 harness 侧 hook 才能拿到 before/after（Demo 用 mock 规避，但要在评估里诚实说明）。
- 我可能判断错的地方：若主流厂商很快把「压缩可解释性」内建进 API（自曝丢弃项与风险），第三方审计层的空间会被压缩；留痕需以「厂商中立 + 保命清单控制 + 跨厂商可比」建立护城河。
