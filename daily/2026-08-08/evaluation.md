## 3. 核心流程是否闭合

闭合。三步主路径完整：
1. **① 扫描台**：mock 仓库 + 5 份指令文件 + 「运行契约扫描」触发确定性终端回放（16 行、可重播），末行给出健康分 44/100。
2. **② 契约账本**：健康分 + 4 类统计卡（冲突/漂移/无法验证/对齐）+ 可搜索、可「只看有问题」筛选、可逐行展开的 12 条声明；每条问题可勾选「采纳对表修复」，健康分随之实时重算（44 → … → 96）。
3. **③ 对表修复**：健康分增量卡（44 → 96）、跨 3 个文件的修复 diff（-/+ 着色）、「修复前 / 后 agent 一次典型执行」的 before/after 对比、可复制的契约体检报告。

## 4. 首屏是否讲清产品价值

讲清了。首屏 claim 条直接对比 HAR（迁移到新契约）、Reference（嵌入相似度看 doc-drift）与本产品（默认已有指令会骗人、专门证伪并对表），3 句话说清「解决什么 / 怎么用 / 增量在哪」。

## 5. 交互是否有断点

无明显断点：

- 账本搜索 / 筛选 / 展开 / 勾选修复 / 一键全部对表 / 重置均可用，健康分联动确定性、无闪烁。
- 复制报告在支持 clipboard 的环境下正常；失败时静默不崩。
- 响应式：窄屏下 diff / before-after / 详情网格自动单列。

## 6. 是否只是概念包装（自嗨检测）

- 是否引用了报告中的具体信号：是。直接锚定报告的 HAR（机器可读契约）、Reference（`check_doc_drift`）与「协作/记忆/审批做成机制」趋势，并对报告「换新契约 / 嵌入相似度」的解法提出了独立质疑。

- 是否是某产品的照抄：否。目标函数与 HAR/Reference 相反（证伪已有指令 vs 产出/度量契约）。

## 7. Demo 的最大问题

判决是**预先设计好的确定性 mock**，没有真正解析自然语言指令、也没在沙箱执行命令。真实产品的两大工程难点——「从自然语言指令抽取可校验声明（需 LLM）」与「在隔离环境执行核对（需 sandbox）」——的误报/漏报率，本 Demo 无法体现，只在文案中如实标注。
