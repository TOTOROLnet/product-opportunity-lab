## 2. 候选机会（3 个，均为创新切入点而非照抄）

### 候选 A：众读 Zhòngdú —— "发送前，先让一屋子目标读者替你读一遍"
- 创新切入点：把"多 AI 同台"从**辩论表演**反转为**接收模拟**。你把一段只发一次、发错就亏的高风险文字（求职信/冷启邮件/融资一句话/相亲简介/难开口的消息）交给一组各不相同的 AI 读者，它们**逐字逐句**地"读"，实时给出注意力曲线、困惑点、反感点，并**逐词高亮出你的目标读者到底在哪一句流失**。它**不替你改写**，只让你看清"落地效果"，把改的决定权留给你。
- 目标用户 / 场景：任何要发出"一次性、高风险文字"的普通人——求职者、找工作/找客户的独立开发者、写融资/pitch 的创业者、发难开口消息的普通用户。
- 五维评分：痛点 4/5，机制新意 4/5，AI 核心度 4/5，一天可行性 5/5，启发价值 4/5 → 合计 **21/25**

### 候选 B：分歧地图 Crux Map —— 多 AI 不给答案，只给"分歧点 → 真正该你定的 3 件事"
- 创新切入点：同样骑 AI Group Call，但服务"个人决策"：不让 AI 替你拍板，而是生成几种**真正不同的决策取向**，标出它们**在哪儿分歧、为什么**，把分歧压缩成少数几个"crux（只有你能回答的问题）"，最后交付"这 3 件事只有你能定"而非一个答案。
- 目标用户 / 场景：面临两难个人决策（要不要接这份 offer、选哪套房、如何处理家庭冲突）的人。
- 五维评分：痛点 4/5，机制新意 3/5，AI 核心度 4/5，一天可行性 4/5，启发价值 3/5 → 合计 **18/25**
- 不选原因：决策辅助赛道拥挤；且"AI 坦诚说'我替你决定不了'"这条脉络（准星/忆证/换挡/风洞/验己/有数）我已反复做过，是**明显变旧的基因**；mock 很难让"真分歧"显得不像脚本。

### 候选 C：递归剧场 RLM Playground —— 递归 Agent 程序的设计期模拟器
- 创新切入点：骑 Prime Agent 的 RLM。做一个**设计期**的可视化 playground / 单步调试器：用 mock 模型编排一段"context 当变量、`rlm(子任务)` 当函数调用"的递归 agent 程序，实时看到上下文变量如何流动、子 agent 如何带独立历史被 spawn、每次递归调用的 token 成本如何累加——在写真实代码前先想清楚一个递归 agent 设计。
- 目标用户 / 场景：混元/agent 平台开发者、想采用 RLM 范式的工程师。
- 五维评分：痛点 3/5，机制新意 4/5，AI 核心度 4/5，一天可行性 4/5，启发价值 4/5 → 合计 **19/25**
- 不选原因：受众窄、偏"概念可视化"，真实 JTBD 不够高频；且紧贴我已重度开采的 agent-runtime 脉络。

## 3. 最终选择

- 选中：**候选 A —— 众读 Zhòngdú**，总分 **21/25**
- 为什么选它（相对其他候选的优势）：
  1. **痛点最普适、最高频、最"发错就亏"**："这段字会不会打动那个人"是求职、冷启、融资、相亲、难开口消息的共同焦虑，而现有写作 AI 只会改语法/语气，答不出"落地效果"。
  2. **机制是全新原语，且天生适合纯前端模拟**：多读者逐字接收 + 词级注意力/困惑/反感热力图 + 流失点定位，是 Vite 静态 Demo 能"3 分钟讲清价值"的可视化交互形态。
  3. **换维度补 2C、跳出旧形态**：连续 4 天技术向 + audit/gate/preflight 形态已做穿；A 是"生成/模拟"型、2C 面向、非把关非计算器，正是记忆里明确建议的新方向。
  4. B 落在我最旧的"诚实/不确定性"基因上，C 受众窄且贴旧脉络——A 在痛点、新意、可行性三项同时占优。

## 4. 深入论证（针对选中机会 众读）

1. 目标用户：要发"只发一次、发错代价高"的文字的普通人——求职者、独立开发者/自由职业者（冷启客户）、早期创业者（一句话融资/落地页）、以及发难开口消息（道歉/请求/边界）的普通用户。
2. 核心痛点（真实、高频、可付费）：**发送前不知道对方会怎么读。**现有做法只有三种，全都差：① 自己猜（有偏差）；② 拉朋友看（慢、碍于情面给不了真话、样本单一）；③ 用 Grammarly/AI 改写（修的是机制与语气，答不出"我的目标读者在第几句就不想看了、为什么反感"）。
3. 现有产品为什么没解决好：写作助手的心智是"帮你把字改好"，产出是**更顺的文本**；但用户真正要的是**接收侧的预演**——不同读者会不会读下去、在哪困惑、在哪反感、在哪流失。这需要"模拟多个不同读者的理解与反应"，是 LLM 才能做的、且当前写作工具没有做的一层。
4. 为什么适合做轻量 Demo：接收模拟可用"脚本化逐字回放 + 词级热力图 + 改前改后对比"完全在纯前端呈现；样本文本、读者画像、逐 span 反应、编辑增量全部 mock，无需任何后端/外部 API，且**可视化本身就是价值证明**。

## 5. 不照抄声明（四项必填）

1. **创新切入点是什么**：把"多 AI 同台"从"辩论表演/替你决策"反转为"**模拟你的目标读者逐字读你这段文字**"，交付一张词级的接收热力图 + 逐读者反应流 + 目标读者流失点，且**只诊断不代写**。
2. **解决的具体问题 / 场景**：发送前预演一段一次性高风险文字（求职信/冷启邮件/融资一句话/相亲简介/难开口消息）会被目标读者如何接收——在哪读不下去、哪句困惑、哪句反感、到底哪一句让人放弃。
3. **相对被参考产品的增量价值（差异点）**：
   - vs **AI Group Call**：它是"围绕一个目标的多 AI 语音辩论"（表演，产出不确定）；众读是"围绕你的具体文字的多读者接收诊断"（工具，产出是可定位到词的热力图与流失点）。
   - vs **写作助手（Grammarly / 各类 AI 改写）**：它们修语法/语气、直接给你改后文本；众读不改写，而是告诉你**特定读者在哪一句、因为什么原因流失/反感**，把改的决定权留给你。
   - vs **B2B 合成用户调研（synthetic user research）**：那类工具面向企业做大规模问卷式画像访谈；众读是 2C、面向"我这一段字"的即时逐字接收预演，轻、快、贴个人场景。
4. **为什么这不是照抄 AI Group Call（本质区别）**：AI Group Call 的对象是"一个目标"、形态是"实时语音辩论"、产出是"听不同意见"；众读的对象是"你写好的一段文字"、形态是"多读者逐字接收 + 词级热力图 + 流失点"、产出是"发送前的接收诊断"。两者只共享"多 AI 同台"这一原语，目标、形态、产出全不同——直接去用 AI Group Call 得不到"我这段字在第几句流失"的答案。

## 6. 不确定性与风险

- 需求侧风险：① 频次——高风险文字并非人人天天写，可能是"重要但低频"；② 用户是否信任 AI 模拟的读者反应能代表真实读者（可信度需靠"逐字定位 + 说明原因"建立，而非给一个玄学分数）。
- 落地 / 技术风险：真实产品里"读者画像的真实性"是死穴——若 persona 只是换皮，反应会千篇一律；需要真正条件化不同阅读动机/耐心/领域背景的 LLM 模拟。Demo 用脚本化反应规避，但必须**如实说明这是 mock 的预计算反应**，不假装在线推理。
- 我可能判断错的地方：① 也许用户更想要"直接帮我改好"而不是"告诉我哪不好让我自己改"——若如此，本产品的"只诊断不代写"原则需要让位于"诊断 + 可选一键改"；② "接收模拟"可能被强写作品牌（Grammarly/Notion AI）顺手补齐为一个功能，护城河更多在**读者画像质量与逐字定位体验**。

- 是否达到 16/25 门槛：**是**
