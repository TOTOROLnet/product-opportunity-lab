# Demo 设计说明 — 2026-08-11

## 1. Demo 名称
众读 Zhòngdú —— 发送前的"读者接收预演台"

## 2. 一句话定位
把你只发一次、发错就亏的一段文字，先交给一屋子各不相同的 AI 读者逐字读一遍，看清他们在哪一句流失、哪句困惑、哪句反感——**只诊断落地效果，不替你改写**。

## 3. 目标用户
要发"一次性、高风险文字"的普通人：求职者（求职信/自我介绍）、独立开发者与自由职业者（冷启邮件/客户提案）、早期创业者（一句话融资/落地页首屏）、以及要发难开口消息（道歉/请求/边界）的普通用户。

## 4. 使用场景
点击"发送"前的最后一刻：我这段字，目标读者会不会读下去？在哪一句就不想看了？哪句让他困惑或反感？——现有工具只会帮我把语法改顺，答不出这些接收侧的问题。

## 5. Demo 策略分型（重要）

- 本机会属于：**■ 可视化/交互类产品**（读者接收的逐字回放 + 词级热力图，是天然可点击、可视化的交互）
- 采用的演示方式：直接做可点击交互 Demo；其中"多读者逐字读你的文字并产生反应"这一 AI 能力，用**脚本化的预计算反应**（mock corpus）驱动逐字回放与热力图，**如实标注这是离线模拟、真实产品由 persona 条件化的 LLM 在线生成**。
- 演示的是**我们分析出的创新切入点**（多 AI 同台 → 接收模拟 + 词级流失点诊断），不是 AI Group Call（语音辩论）或写作助手（代写）的克隆。

## 6. 核心流程
（用户从进入到"看懂价值"的主路径，3 分钟内可完成）
1. 在**围读台**选一段样本文字（求职信 / 独立开发者冷启邮件 / 一句话融资）+ 一组读者（目标读者 + 3 个不同画像），点"开始围读"。
2. 观看**逐字回放**：文字按阅读顺序逐句高亮，右侧每位读者的注意力条实时起伏、内心反应逐条冒出，句子上落下困惑(?)、反感(!)、流失(✕)标记；回放结束定位"目标读者流失于第几句"。
3. 切到**接收热力图**：同一段文字上叠加词/句级热力（投入=绿 / 困惑=黄 / 反感=红 / 略读流失=灰），悬停看是哪位读者、什么反应；给出"目标读者流失点 + Top3 摩擦点（含原因）"，**但不给改后文本**。
4. 切到**改前改后**：勾选几个脚本化"改法"（如"删掉自夸开头/把请求前置/加一句对他的具体价值"），实时看到流失点后移、注意力抬升、反感清除，以及接收分（0–100）改前→改后的变化——直观证明增量在"接收"而非"语法"。

## 7. 页面结构（<= 3 个主要页面，单页 3 Tab + 顶部配置区）
- 配置区（常驻顶部）：选样本文字、选读者面板、"开始围读"。
- 页面 1 · **围读台（Reading Room）**：逐字回放 + 每读者注意力条 + 实时反应流 + 目标读者流失点。
- 页面 2 · **接收热力图（Heatmap）**：词/句级热力叠加 + 悬停详情 + 流失点与 Top3 摩擦点（含原因，不代写）。
- 页面 3 · **改前改后（Before / After）**：脚本化改法开关 + 接收分改前后对比 + 流失点位移可视化。

## 8. 关键交互
- "开始围读"→ 以 `setInterval` 逐事件回放（事件流 = 有序的 `[读者, 句子, 反应类型, 注意力增量, 一句话反应]`），可暂停/重播。
- 热力图 span 悬停 → 弹出"哪几位读者 + 各自一句话反应"。
- 改法开关（多选）→ 纯函数按脚本增量重算接收分、流失点、各句热力等级，界面即时联动。
- 读者面板可切换"目标读者"是谁 → 流失点判定随之变化（体现"对不同读者，落地效果不同"）。

## 9. 使用的 mock 数据
（全部为 mock，不接真实后端/外部 API）
- `samples`：3 段样本文字，每段切成有序 `sentences[]`（句 = 若干可高亮 span）。
- `readers`：读者画像池（目标读者 + 挑剔招聘经理 / 匆忙扫读者 / 怀疑者 / 领域专家等），每个含耐心值、关注点、语气。
- `reactions`：脚本化的"读者 × 句子 → 反应"表：反应类型（engaged/confused/skeptical/bored/drop）、注意力增量、一句话内心反应。
- `edits`：每段样本 3 个脚本化"改法"，各自声明对哪些句子的反应/注意力增量（用于改前改后重算）。
- `engine.ts` 纯函数：`replayEvents`（生成回放事件流）、`aggregateHeatmap`（句级反应聚合→热力等级）、`findDropoff`（目标读者首个 drop 句）、`topFrictions`（按严重度排序）、`receptionScore`（0–100）、`applyEdits`（套用改法后重算）。数值先用一次性 `_verify.ts`（esbuild→node）核对"改前分低/流失早、改后分高/流失后移"符合设计，再接 UI。

## 10. 明确不做什么
- 不做登录 / 用户系统
- 不接数据库 / 支付 / 外部私钥 / 真实 API / 真实 LLM 推理（读者反应为离线脚本，界面显式标注）
- 不做生产级后端
- 不"帮你改写文本"——本 Demo 刻意只诊断、不代写，以体现与写作助手的本质区别

## 11. 成功体验标准
- 用户 3 分钟内能说出："它解决什么问题（发送前预演目标读者的接收）、怎么用（选文字+读者→看逐字回放/热力图→试改法）、增量在哪（定位到具体某句的流失/反感原因，而非改语法）"。
- 首屏即讲清"这不是又一个改写工具，而是接收预演台"。
- 改前改后能让人直观看到"接收分与流失点随'改法'明显变化"，且改的是**结构/价值**而非语法。
