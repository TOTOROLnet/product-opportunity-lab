## 1. 报告事实 vs 我的独立判断

| 维度 | 报告怎么说（参考资料） | 我作为创业者的独立判断 |
| --- | --- | --- |
| 今日主线 | 技术向"零历史命中"硬货领跑（Prime Agent 自我改进 harness / Paritok 压缩网关 / oqoqo agent-first eval） | 认同这批技术信号很硬。但报告把它们各自当"给平台方的能力"看；我看到的是**一个共同的下游后果**：当 agent 跑得越久、越自治、还会**改写自己**，把任务委派出去的那个**人类**将越来越"看不懂它到底干了什么"。报告没人替这个"人"说话。 |
| Prime Agent 的 Continual Harness | 定位为"可演进 harness 最清晰的范式模板"，亮点是 agent 能读轨迹自我精炼、按 ID 可回滚 | 技术上认同。但报告只从"agent 怎么变强"讲，**漏了对称的一面**：`/refine` 意味着 agent 这一趟不只改了你的代码，**还改了它自己**（新增/修改了 skill、memory）。用户下一次面对的是一个"已经和昨天不一样"的 agent——**"它这次给自己改了什么"是一个全新的、必须被人读懂的对象**，目前没有任何产品在服务它。 |
| oqoqo 的 "agent 是软件主要用户" | 用来支撑一个 **eval** 平台（测 agent 能否用你的产品，产出通过率/摩擦指标） | 我认同这个论断，但**拒绝把它做成又一个打分/验收工具**（本实验室 08-09 正名、07-29 准星已把"评测/校准"脉络做穿）。同一论断的另一面是：如果 agent 是主要执行者，那么**人退居"事后审阅者"**——人最缺的不是给 agent 打分，而是**在委派完成后快速"补看懂"发生了什么**。 |
| Paritok 可逆压缩 | 为 agent 省 token、把成本和上下文长度解耦 | 认同其工程价值。但"可逆压缩"本质是**分层保真的信息折叠**——这启发我：给人看的东西同样需要"先给要点、要细节再展开"。不过若只做"折叠 agent 日志少给点信息"，就落回 08-11 记忆里点名过的 audit/compaction 老形态，不做。 |
| 长任务自治的落点 | 报告聚焦"能力"（更省、更小、跑得更久、会自改） | **我的独立判断：能力越强，"理解债"越重。**一次 4 小时的自主运行 = 几十步工具调用 + 几百行 diff + 几处自我改写，散落在原始日志里。人要么不看（失控），要么逐行爬（昂贵）。**"运行结束后 3 分钟看懂并只盯需要我拿主意的 2–3 处"——是一个被整份报告系统性忽略、却随自治度上升而高频化的真需求。** |

（我**质疑**报告的隐含视角——它默认读者是"造 agent 平台的人"，于是所有信号都被读成"能力"；我**补充**一个报告没有的视角——"把活委派给 agent 的人"，从这个视角看，Prime Agent/Paritok/oqoqo 三条信号共同指向同一个缺口：**自治 agent 的"可理解性/可补看性"**。这不是给 agent 打分（那是 eval），也不是拦它放不放行（那是治理），而是**帮人读懂**。）

## 2. 候选机会（3 个，均为创新切入点而非照抄）

### 候选 A：随读 Suídú —— 自主 Agent 长时运行后的"3 分钟补看"阅读器
- 创新切入点：把一整段自主 agent 运行（**含它给自己改了什么**）从"原始轨迹 + 大 diff"重构成一条**可滚动的叙事时间线**——按"确认目标 → 首次尝试 → 遇阻转向 → 收敛 → 自我修订 → 收尾"分章，每章一句"发生了什么 & 为什么"，可展开到真实 diff/工具调用；再织入两条特别通道：**「它替我做的假设」**（你可能不同意的判断）与**「悬而未决」**（未完成/待你确认），右栏「只盯这些」把需要你拿主意的 2–3 个岔口顶到最上面。**它不打分、不放行、不判对错，只帮你"读懂"。**
- 目标用户 / 场景：任何把任务委派给自治/后台/过夜 coding agent 的人——用 Cursor 后台 agent / Claude Code / Devin 式 agent 跑长任务的开发者与 Tech Lead，一觉醒来 / 一个会开完面对一大堆变更却没法快速接手。
- 五维评分：痛点 4/5，机制新意 4/5，AI 核心度 4/5，一天可行性 5/5，启发价值 4/5 → 合计 **21/25**

### 候选 B：随附手册 Kit-for-Agents —— 为"以 agent 为用户"的产品生成并现场试用的接入手册
- 创新切入点：骑 oqoqo 的论断（agent 是主要用户），但**不做 eval/打分**，做**生成 + 现场体验**：喂进你产品的原始面（endpoints / CLI --help / 报错目录），自动起草一份"面向 agent 的使用手册"（配方、不变量、易错点、机器可读报错），并让你**扮演一个 agent** 只靠这份手册去完成一个任务，亲身感到哪里说不清、当场改手册。
- 目标用户 / 场景：想让自家 API/SDK/CLI "agent-native"、准备写 `llms.txt` / MCP tool 描述的产品团队。
- 五维评分：痛点 3/5，机制新意 4/5，AI 核心度 4/5，一天可行性 4/5，启发价值 4/5 → 合计 **19/25**
- 不选原因：「agent 作为消费者」目前对多数团队还是**新兴、非高频**需求，痛点强度偏弱；且"扮演 agent 读手册"在纯前端 mock 下偏抽象，3 分钟讲清价值的确定性不如 A。

### 候选 C：折叠术 Foldcraft —— 给人读的"可逆保真"长文阅读画布
- 创新切入点：把 Paritok 的"可逆压缩"从**给 agent 省 token** 反转为**给人省注意力**：一篇很长的 AI 产物（研究报告 / code review / 会议纪要）里每一段都有多档保真度（标题 → 要点 → 全文），你像缩放地图一样丝滑收放，可"钉住"关键事实防止被折叠。
- 目标用户 / 场景：每天被大段 AI 输出淹没的知识工作者。
- 五维评分：痛点 4/5，机制新意 3/5，AI 核心度 3/5，一天可行性 5/5，启发价值 3/5 → 合计 **18/25**
- 不选原因：语义缩放 / 渐进式披露（大纲、折叠、zoom UI）已有大量前作，机制新意与"非照抄"说服力弱；且演示重心在 UI 交互，AI 核心度在纯前端 Demo 里不易凸显。

## 3. 最终选择

- 选中：**候选 A —— 随读 Suídú**，总分 **21/25**
- 为什么选它（相对其他候选的优势）：
  1. **痛点最真、随趋势高频化**：报告整份都在说 agent"跑得更久、更自治、会自改"（Prime Agent/Paritok/oqoqo/趋势 1&2）——自治度越高，"我委派出去的这段到底干了啥"的理解债就越重。这是被报告系统性忽略、却正在变高频的真需求；A 直接服务它。
  2. **机制是全新原语、且天生适合纯前端"模拟体验 + 价值可视化"**：把一段 mock 的 agent 运行重构成"叙事时间线 + 假设通道 + 悬案通道 + 只盯这些"，是 Vite 静态 Demo 能在 3 分钟讲清价值的可视化交互形态；且能内置 before/after（原始 43 行日志 vs 3 分钟叙事）把增量做到可感。
  3. **踩中一条对本实验室全新的"基因"**：过去 40 天里 audit/gate/放行（归位/对表/正名）、preflight/计算器/判决（风洞/换挡/预调）、"AI 诚实说不/认怂"（准星/忆证/验己…）、接收模拟（众读）都已做过。A 的基因是**"叙事 / 阅读理解 / 帮人补看懂"——不打分、不放行、不判对错**，是明确未被开采的新方向。
  4. **对 Prime Agent 最独特之处有专属回答**：市面上"会话摘要"只会总结 agent 对项目做了什么；A 额外服务**"它这次给自己改了什么"**（Continual Harness 的自我修订），这是通用摘要器和"拦截自改"的治理工具都没做的一层。
  5. B 需求偏新兴低频、Demo 偏抽象；C 语义缩放前作多、非照抄说服力弱——A 在痛点、机制新意、可行性三项同时占优。

## 4. 深入论证（针对选中机会 随读）

1. 目标用户：把任务**委派**给自治/后台/过夜 agent 的开发者与 Tech Lead——用后台 coding agent 跑重构/修 flaky 测试/接需求的人；他们的共同处境是"回来面对一堆已经发生、但自己没在场看的变更"。
2. 核心痛点（真实、高频、可付费）：**长时自治运行结束后，人没法低成本地"接手理解"。**现状只有两条差路：① **不看**——直接信任并合并，把 agent 的隐藏假设与半成品一起吞下（失控）；② **逐行爬**——打开几十步工具日志 + 几百行 diff 自己重建来龙去脉（昂贵、且极易漏掉埋在中间的假设与自我改写）。缺的是一层"**替我把这段读懂、并把该我拿主意的少数几处顶出来**"。
3. 现有产品为什么没解决好：
   - **agent 可观测性 / trace 工具（LangSmith 等）**：面向"调试"，给的是原始 span/trace，越全越难"补看"，服务的是工程排障不是人类接手理解。
   - **代码 diff / PR 视图**：只呈现"改了什么"，不呈现"为什么这么改、在哪拐了弯、它替你假设了什么、还差什么"，更不呈现"它给自己改了什么"。
   - **通用"会话摘要"**：一段扁平总结，不可滚动追溯、不区分"需要你决定 vs 只是过程"，且完全无视 Continual Harness 式的自我修订。
4. 为什么适合做轻量 Demo：整段运行可用**脚本化的 mock 轨迹**呈现——章节、每章的 diff/工具调用、假设、悬案、自我修订、原始日志全部 mock；"补看用时 vs 逐行爬用时"用可解释的启发式估算；叙事时间线 + 展开细节 + "只看需要我决定的"过滤 + before/after 对照，**可视化本身即价值证明**，无需任何后端/外部 API。

## 5. 不照抄声明（四项必填）

1. **创新切入点是什么**：把"长时自治 agent 运行"这一原本散落在原始轨迹里的过程，重构成一条**给人读的叙事时间线**——分章的"发生了什么 & 为什么" + 「它替我做的假设」 + 「悬而未决」 + **「它给自己改了什么」**（Continual Harness 自我修订的可读变更日志） + 右栏「只盯这些」，**只帮人读懂、不打分不放行不判对错**。
2. **解决的具体问题 / 场景**：把任务委派给过夜/后台自治 agent 后，如何在 **3 分钟内**补看懂这一整趟（含它对项目和对自己各做了什么），并只盯住需要你拿主意的 2–3 个岔口，而不必逐行爬几十步日志和几百行 diff。
3. **相对被参考产品的增量价值（差异点）**：
   - vs **Prime Agent（被参考产品）**：Prime Agent 让 agent **会**自我改写与长时自治（生产端能力）；随读服务其**下游**——当 agent 真的改了项目也改了自己，帮委派它的**人**把这一切读懂。前者造能力，后者补上能力带来的"理解债"。
   - vs **oqoqo**：oqoqo 是 **eval**（给 agent 用你产品的能力打通过率/摩擦分，产出是指标与验收）；随读**不打分**，产出是一段**可读的过程叙事** + 该你决定的少数岔口。评的是"能不能用"，读的是"这趟到底干了啥"。
   - vs **agent 可观测性/trace 工具**：那类工具给**越全越好的原始 trace** 供工程调试；随读做**减法与叙事**，给非在场者"接手理解"，并显式分出"需要你决定 vs 只是过程"。
   - vs **通用会话摘要 / diff 视图**：摘要是扁平总结、diff 只讲"改了什么"；随读是可滚动追溯的叙事 + 假设/悬案/自我修订三条特别通道，且专门服务 Prime Agent 式的"它给自己改了什么"。
4. **为什么这不是照抄 Prime Agent（本质区别）**：Prime Agent 的对象是"让 agent 运行时能自我演进"，形态是 harness/运行时，产出是更强的 agent；随读的对象是"一段**已经发生**的运行"，形态是给人看的**只读叙事阅读器**，产出是"3 分钟补看懂 + 只盯 2–3 处"。二者只共享"自治 agent 的运行轨迹"这一素材，目标（造能力 vs 帮人读懂）、形态（运行时 vs 阅读器）、产出全不同——直接去用 Prime Agent 并不能得到"我这趟委派到底发生了什么、哪几处该我拿主意"的答案。

## 6. 不确定性与风险

- 需求侧风险：① **频次依赖自治度**——只有当人真的"把长任务委派给会自主跑很久的 agent"成为日常，这个补看需求才高频；2026 年趋势明显向此，但普及度仍在早期。② 用户可能更想要"**你替我把关/直接告诉我能不能合并**"（判决）而非"帮我读懂让我自己拿主意"——若如此，随读的"不打分不放行"原则需让位为"读懂 + 可选的一键校验"。
- 落地 / 技术风险：真实产品里，"把原始轨迹压成忠实、不误导的叙事 + 准确抽出隐藏假设/自我修订"是**死穴**——叙事若失真或漏掉关键假设，比不看更危险，信任瞬间崩。Demo 用脚本化 mock 规避，但**必须如实标注这是 mock 的预置轨迹与叙事，不假装在线推理**；真实版必须做到"每条叙事都能一键展开到它所依据的原始步骤/diff"（可追溯性 = 信任基石）。
- 我可能判断错的地方：① "补看"也许会被 Cursor/Claude 等平台方顺手做成一个内置面板，护城河更多在**叙事质量、假设/自我修订抽取的准确度、以及"只盯这些"的排序是否真的顶出了对的东西**；② 我把"它给自己改了什么"当作差异化亮点，但当前只有 Prime Agent 一家把自我修订产品化，若该范式短期不普及，这条通道的现实价值会打折（不过它本就是报告 17/18 的头号信号，押注其代表方向是合理的）。
