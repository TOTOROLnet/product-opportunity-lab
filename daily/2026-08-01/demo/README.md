# 风洞 WindTunnel — WASM agent 运行时「迁移前风洞」

> product-opportunity-lab · 2026-08-01 · 纯前端静态 Demo（Vite + React + TypeScript）

把你 agent 的**真实工具负载**放进「风洞」，在真正投入迁移工时**之前**，算清它在进程内 WASM
agent 运行时（如报告里的 agentOS）里**到底能不能跑、到底省多少**——用你自己的负载说话，而不是
照搬厂商头条的「成本便宜 254×」。

## 它解决什么

agentOS 这类进程内 WASM 运行时把「每个 agent 一台 microVM/容器沙箱」的重资产模型，改成便宜得多的
进程内库（官方头条：冷启动 92× / 内存 47× / 成本 254×）。但报告自己也承认：**WASM 有兼容边界——
x86 二进制 / GPU / ffmpeg / 原生扩展仍需「按需 mount 真沙箱」**。这些 fallback 是**静默**发生的，
迁完之后你才会在账单和 P99 延迟里发现「怎么没省下来」。

风洞坐在**采纳决策的上游、厂商中立**：给它你的工具负载画像，它做三件事——
1. **兼容 X 光**：每个工具在 WASM 运行时里的命运（native 便宜 / mount 按需真沙箱 / blocked 跑不了）+ 原因；
2. **诚实成本/延迟**：你这套负载的真实倍数（而非头条 254×）、before/after 成本、冷启动 P99 与 fallback 尖峰；
3. **出厂判定 + 改造建议**：迁 / 谨慎迁 / 先改造 / 别迁，且敢给「不建议迁移」的结论。

## 核心洞察（阿姆达尔式成本地板）

真实倍数 = 1 ÷（native部分 / 254 + 重活部分 × 开销）。**只要 5% 的负载是重活，254× 就塌成 ~16×；
到 20% 只剩 ~4×。** 「阿姆达尔滑杆」页可交互看到这条塌陷曲线。

## 页面

1. **风洞台 · 兼容 X 光**：负载选择器 + 工具分层表 + 254×（划掉）vs 你的真实倍数。
2. **成本 × 延迟**：分层堆叠成本条、冷启动 P99 对比、fallback 尖峰时间线。
3. **阿姆达尔滑杆 · 出厂判定**：交互滑杆看 254× 塌陷 + 四色判定卡 + 逐项改造建议 + 诚实免责声明。

预置 4 类代表性负载：编码代理（~34× 值得迁）/ 数据分析代理（~6.6× 谨慎迁）/ 爬取代理
（~2× 先改造）/ 媒体处理代理（~0.78× 不建议迁、反而更贵）。

## 本地运行

```bash
npm install      # 安装依赖
npm run dev      # 本地开发（默认 http://localhost:5173）
npm run build    # 生产构建，产物在 dist/
npm run preview  # 预览生产构建
```

## 技术与约束

- Vite + React + TypeScript；`vite.config.ts` 设 `base: './'`，可部署到任意 GitHub Pages 子目录。
- 引擎 `src/logic/engine.ts` 为**确定性可解释公式**（非 LLM、非黑箱）；数据 `src/data/workloads.ts` 全部为 mock。
- **不接**后端 / 数据库 / 支付 / 登录 / 外部 API / 真实运行时；是**方法论演示**，非精确报价。

## 与被参考产品的区别（非照抄）

- vs **agentOS**：它是执行引擎（卖运行时、有动机报喜）；风洞是**决策前的仿真 + 诚实读数**（厂商中立、
  可能劝退你别用 agentOS）。位置、对象、激励完全相反，一行 agent 都不真的跑。
- vs **TraceLLM / OTel 观测**：它们是**事后**看已发生的成本；风洞是**采纳前**预判（还没迁就先算）。
