## 4. 深入论证（针对选中机会）

1. 目标用户：已经在用「brief→成片」类 agent（Vizard / Omniwork / CapCut 智能剪等）、但在**改稿环节被卡住**的创作者、营销、独立开发者、课程/带货口播作者。
2. 核心痛点（真实、高频、可付费）：初稿常常「大方向对、局部不对」。今天要改，只有两条烂路——
   - **回时间线**手动剪：等于否定了「无时间线」的全部价值，且用户本来就是为了不学剪辑才来；
   - **整片重生成**：丢掉本来已经满意的 80%，还要再烧一次生成时间与成本，且结果可能连之前好的地方也变了（生成不确定性）。
   用户**没有第三条路**去「只改这一段、并保住其余」。这道坎每做一条视频都会撞到，是付费与留存的直接决定因素。
3. 现有产品为什么没解决好：Vizard 把力气全压在「生成流水线（8 个角色）」和「对话式修改」上——但一个聊天框面对一整条多镜头视频，**缺少精确作用目标与保护机制**：说不清改哪、也锁不住已认可的镜头。CapCut/剪辑器则是另一极端，把人拽回专业时间线。两端都没有「导演对剪辑师说戏」这种**镜头级、意图级、可保留**的中间态。
4. 为什么适合做轻量 Demo：核心体验是「看初稿 → 按镜头说戏 → 看改动前后 diff」，天然可用 storyboard 卡片 + 笔记面板 + 对比视图表达，全部可 mock，纯前端静态即可讲清价值，不需要真实生成模型。

## 5. 不照抄声明（四项必填）

1. **创新切入点是什么**：一个厂商中立、坐在「brief→成片」agent 之上的**导演改稿层**——把迭代重构为「镜头级导演笔记 + 锁定已认可镜头 + 只重生成被点名镜头 + 改动前后预览」，取代「回时间线」与「整片重来」，成为改稿的主界面。
2. **解决的具体问题 / 场景**：brief→成片 agent 最容易死掉的**改稿闭环**——初稿 80% 对、最后 20% 改不动：既不能精确指向某个镜头，也无法保护已认可的部分，只能整片重来、丢掉好的、再烧成本。
3. **相对被参考产品的增量价值（差异点）**：我**不做生成**。Vizard/Omniwork 拥有「brief→初稿」；我拥有「初稿→成片」——让它们「无时间线」的承诺在**迭代中依然成立**：保留已认可镜头、只重生成被点名的、可见的 keep/regenerate diff 与「保留 X 镜、重生成 Y 镜」的成本/保留度可视化。厂商中立，可叠在任意生成 agent 之上。
4. **为什么这不是照抄 Vizard（本质区别）**：Vizard = 生成流水线（8 角色 brief→成片）+ 一个用于修改的聊天框；说戏 = 生成之上的**导演层**——结构化的镜头级笔记与快捷控件、显式的锁定/保留语义、keep-vs-regenerate 的改动 diff 与成本/保留度可视化。**不同的活（改稿而非生成）、不同的交互原语（导演笔记而非聊天）、不同的价值（保留 + 精确 + 省成本）**。照抄 Vizard 意味着再造一个生成器——我刻意不生成。

## 6. 不确定性与风险

- 需求侧风险：改稿层的价值高度依赖上游「brief→成片」agent 先跑到有规模的用户盘；若生成 agent 自己把改稿闭环做透，中间层空间会被压缩（缓解：厂商中立 + 跨 agent，做「所有生成器共用的导演台」）。
- 落地 / 技术风险：真正产品化需要生成器暴露**镜头级重生成 API 与稳定的 seed/锁定**能力；现实里很多生成 agent 只能整片重来，「只重生成被点名镜头」可能退化为「局部近似」。Demo 里以 mock 引擎演示理想形态，需在 evaluation 里诚实标注这是**期望形态而非已证明的后端**。
- 我可能判断错的地方：也许多数轻量用户对 80% 的初稿就满意、根本不改稿，那么改稿层是伪高频；或对话式修改在模型足够强后已「够用」，镜头级结构反而显重。需要早期用真实创作者验证「改稿撞墙」的发生率与付费意愿。
